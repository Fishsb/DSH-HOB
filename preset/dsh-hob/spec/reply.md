# 回复形态（三种）· 行为规格

> ⚠ 机读骨架在 `workflow.toml` 的 `[[reply]]`；本文件是散文解释，两边用 `id` 对应。

## 判定只有一个问题

**这一轮有没有真的把活派给 developer session？**

- **派了** ⇒ `two-part`：实施指令 + 简要说明；实施指令**保持满技术密度**。
- **没派**（讨论、或把决策抛给用户）⇒ `brief-only`：**只有**简要说明，**一个指令块都不许出现**。
  ⛔ 不许为了凑形态编一个任务，⛔ 不许写「本轮无指令」这种占位，⛔ 不许留空的实施指令壳子。
- **用户在问信息** ⇒ `question-turn`：**第一句就是答案**；四块**不出现**。

## ⛔ 三种错法（实测踩过）

1. 在回复里写实施指令，但**从未真的派出去**。
2. 派出去了，又把指令**粘回给用户**看。
3. 给讨论轮 / 决策轮挂一个指令块 —— 它**没有读者**。

## 两个节名只属于「回复用户」

`实施指令` / `简要说明` **只**用在给用户的回复里。
developer session 回来的报告**不用**这两个标题 —— 它用自己那六节
（结论先行 / 前置读数 / 做了什么 / 未做到·未验证·与指令不符 / 待决问题 / 建议）。
⚠ **两种形态服务两个读者**；混用会让报告顶着你的节名回来，并开始**替你下发下一轮活**
（实测发生过）。
