### E-133 · **写死的"成员清单"不只是会过期 —— 新增成员会整个逃出判据视野**（"不扩范围就永远看不见"）

**现象**：`scripts/check-doc-shape.mjs` 里那张正本清单是**手抄的常量**：
```
const B_FILES = ['PROJECT.md', 'DECISIONS.md', 'USER-DECISIONS.md', 'CONTEXT.md']
```
断言 B（无补丁式说明）/ J（节标题不重复）/ D（归档引用存在）/ D′（作业书存在）/ I（无未渲染标记）
**五条全用 `for (const f of B_FILES)` 循环**，C 组另抄了一份同样的四个文件名。
⇒ 在隔离副本给账本根**加第 5 份 `*.md`**（`FIFTH.md`，内含**悬空归档引用** + **未渲染标记** 两样真违规）：
```
  ✓ D ✓ 四份正本里的 15 处具名归档路径引用，**全部真实存在**
  ✓ I ✓ 四份正本里**没有**未渲染的占位标记（4 份逐份扫描，命中 0 处）
判定：PASS        （exit 0，对新增文件**零提及**）
```
**那 5 条断言一条都没扫它** —— 不是"扫了没报"，是**根本没进循环**。
最刺眼的一支：把它**同时写进 `.gitignore`** 之后，C 组照旧打印
`✓ C ✓ 账本仓：四份文档与 archive/ 均未被忽略（5 项逐条实测）` ——
**一份"该入库"的正本被静默排除，而专门管这件事的断言连它的名字都没见过**。

**根因**：**手抄的清单是一份"闭集"** —— 它描述的成员集合**由写字的人当时的记忆决定**，
而不是由"成员实际在哪"决定。⇒ 判据的**覆盖面**与**被检查对象**之间**没有任何机制**保证一致：
- 新成员加进来时，**没有任何东西告诉任何人"该更新那张清单"**（本轮实测：全套收尾命令
  **对新增正本零提及、也没有任何一条要求改文档**）；
- 台账上"四条断言全绿"，而**实际覆盖面已经缩小了** —— 这是**假绿**，
  不是"过期读数"：`E-117` 讲的是"数字会过期"，本条讲的是"**数字所代表的那个集合**会漏"。
⚠ 与 **E-110 同族但不同**：E-110 是"**扩范围**会连坐另一条断言"（改动方看不见副作用）；
本条是"**不扩范围**就永远看不见新成员"（**没有改动方**，所以更静默）——
E-110 的触发条件是"有人动手"，本条**不需要任何人动手**。

**正确做法**：
① **清单改成派生值，⛔ 不手抄**（结构解：让数量/成员**无处可写**）：
   从**账本根**取 `readdirSync(LEDGER_ROOT, { withFileTypes: true })` ⇒
   过滤 `isFile() && name.endsWith('.md')` ⇒ `.sort()`（**一层、非递归、排序稳定**）。
   本轮即把 `B_FILES` 改为 `const B_FILES = PRIMARY_FILES.files`（写死数组**整个删掉**）。
② **同一事实只留一个来源**：C 组原先另抄了一份同样的名单 ⇒ 改为 `...B_FILES.map(...)`
   （同一个事实写两处 = **E-130 同病**：一处改了另一处没改，两面一起瞎）。
③ **空结果必须 FAIL，⛔ 不许静默通过**：清单为空时每个消费方都会"扫 0 份 ⇒ 报 ✓" ——
   那正是**判据改哑**与**判据改对**输出相同（**E-126**）。
   ⇒ 显式 `bad()` 并打出**可读断言行**（**E-112**），例如
   「正本清单**派生为空** ⇒ B / J / C / D / D′ / I 全部未执行（不按通过处理）」+ 原因行。
④ **输出文案里的数量同批改成派生**：`四份正本` ⇒ `${B_FILES.length} 份正本`
   （一句话里写死数量就是 **E-117** 的原形；本轮连 `I ✓ …（4 份逐份扫描）` 一并改掉）。
⑤ **验收必须成对**：**正例被咬 + 反例全绿 + 空清单 FAIL** 三样齐才算成立 ——
   只验"正常账本仍绿"会把"判据改哑"与"判据改对"变成同样输出（**E-126**）。
   本轮三样实测：正例 ⇒ `✗ D 正本 FIFTH.md:3 引用了**不存在**的路径` + `✗ I 5 份正本里存在**未渲染的占位标记**`（exit 1）；
   反例 ⇒ `PASS`（exit 0）；空清单 ⇒ FAIL + 上述断言行。

**代价与处置**：第 70 轮在隔离副本**发现并如实上报**（未动真账本）；
⚠ 同轮还抓出"**没有任何命令要求任何人重写文档**"—— 这证伪了第 69 轮那条
「结构性变更必然伴随文档重写 ⇒ 存量不单开轮」的裁定前提 ⇒ **裁定被推翻**，
第 71 轮改为**把清单派生化**（改动面 = 1 个脚本，未新增机制）。

**出处**：2026-10-11 **第 70 轮**发现（隔离副本 `/tmp/r68`；作业书 `TASK-R70.md`）·
**第 71 轮**落地（作业书 `TASK-R71.md`；工作区提交 `f8f5018`；
`scripts/check-doc-shape.mjs` 新增 `derivePrimaryFiles()`）。
同族 **E-110**（扩范围连坐 —— 本条是它的**反面**：不扩范围则永久漏）·
**E-130**（同源同病）· **E-117**（写死读数）· **E-126**（判据须成对验）·
**E-112**（FAIL 要可读）· **E-70 / E-73**（清单漏一项就静默出事）。
机检关联：**修复本身在跑** —— `check-doc-shape.mjs` 的 `B_FILES` 派生自 `derivePrimaryFiles()`，
空清单 **FAIL**；且 `check:gitignore` 的 C 组随清单扩缩（正例实测 `4 份 → 5 份`、项数 `5 → 6`）。
⚠ ⚠ **但「不许退回去手抄」这一步没有执行器**：第 71 轮**实测过回退**——把 `B_FILES` 改回写死数组后，
再放一份带悬空引用的第 5 份正本，`check:gitignore` **照样 PASS、零提及**。
⇒ 完整判据 = **「派生之后的空清单会 FAIL」**（有机器）；**「有人把它改回手抄」无人拦**（无机器）。
⇒ 如实登记：机制有效、**回归防护缺席**（§5.1 表里本行第 3 列因此标 `未机器化`）。
