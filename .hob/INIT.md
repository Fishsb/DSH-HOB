## 3. 第 2–3 步 · 四份正本从哪来 · 卷怎么建

### 3.1 四份正本 —— **三份有模板、一份没有**（⚠ 这是最容易踩的一处）

| 正本 | 从哪来 | 谁填 |
|---|---|---|
| `CONTEXT.md` | **模板** ✅ `.hob/templates/CONTEXT.md` | 复制后替换占位（`[日期]` / `[谁]` / `第 N 轮`） |
| `DECISIONS.md` | **模板** ✅ `.hob/templates/DECISIONS.md` | 同上（模板里的 `CHG-000` **是有意的占位号，⛔ 别当残留改掉**） |
| `USER-DECISIONS.md` | **模板** ✅ `.hob/templates/USER-DECISIONS.md` | 同上（`UD-00` 同理） |
| **`PROJECT.md`** | ⚠ **没有模板** —— **须自行起草** | ⚠ **这是有意的**：方案是**逐项目唯一的整篇文档**，与"同构空模板 + 每项目填条目"的账本形态本就不同 ⇒ ⛔ 别去"补一个方案模板" |

**命令（三份有模板的）**：

```bash
NEW="<ledgerHome>/<工作区名>"

for f in CONTEXT DECISIONS USER-DECISIONS; do

```

⚠ **`PROJECT.md` 要自己写**：**建议只留 文件头 + 项目概览 + §0**（它是**地图**），正文按节落 `volumes/plan/`。

### 3.2 卷怎么建 —— **按需建，一卷一份索引**

**卷 = 条目正文的落点**（**一事一文件**）。四类卷（**用不用由项目定**）：

| 卷 | 装什么 | 文件名形如 |
|---|---|---|
| `volumes/decisions/` | 方案变更记录 | `CHG-<编号>.md` + `INDEX.md` |
| `volumes/user-decisions/` | 用户决策记录 | `UD-<编号>.md` + `INDEX.md` |
| `volumes/plan/` | **`PROJECT.md` 的正文按节** | `<nn>-<slug>.md` + `INDEX.md` |
| `volumes/context/` | **`CONTEXT.md` 撞读上限时**的移出件 | `<nn>-<slug>.md` + `INDEX.md` |

- ⚠ **每一卷必须有 `INDEX.md`**，且**两向完整**（索引点名的文件必须存在；卷内每份必须被点名）。
- ⚠ **空卷根 / 空卷 ⇒ FAIL**（"扫 0 份报 ✓"就是假绿）。
- ⚠ **卷按需建**：一开始可以一卷都不建；**用到哪一卷就建哪一卷**（⛔ 别预先堆空目录）。
- ⚠ `runtime/` 是**自忽略**的运行态；`backups/` 是**改前备份**（**不进 git**）。

#### 3.2.1 ⚠ ⚠ **编年体陷阱** —— 开账本时就要防（**2026-10-14 实测教训**）

⚠ ⚠ **本节是"项目跑起来之后"才最容易踩的坑**，而它**在开账本时看一眼就能防住**。

**陷阱长什么样**：把 `CONTEXT.md` 当**流水账**写 —— **每轮追加一个带时间戳的章节**
（"（2026-10-12 21:4x）…"、"第 N 轮…"）⇒ 它**按定义就会无限增长**。

**实测代价**（另一项目的真机读数，⛔ 不是推测）：
`CONTEXT.md` 涨到 **261806 字节**、`DECISIONS.md` **261018**，而单文件上限是 **65536**
⇒ **主持人在 `read_contracts` 上只能读到 25%** ⇒ **在"半盲"状态下主持了一整个项目**。
⚠ 更值得记的是：**那个项目的 `CONTEXT.md` 自己登记过"本账本需轮转（旧段迁 `archive/`）"——
而且写了两次 —— 但那只是"记了一笔"，没有任何东西会因此变红**，于是**一直没执行**。

**⇒ 开账本 / 每轮收尾时的两条硬口径**：

| # | 口径 | 判据（可当场跑） |
|---|---|---|
| **1** | **`CONTEXT.md` 只写"现在是什么样"，⛔ 不写编年流水** | 出现 `## …（<日期> …）` 或 `第 N 轮` 这类**时间戳章节标题** ⇒ **该段属于历史，应进 `volumes/context/` 或 `archive/`** |
| **2** | **加内容之前先算一次**（含卷） | 对**每一份会被读到的文件**：`wc -c` **< 上限**（上限值**从预设行读**，⛔ 不硬编码）。⚠ **"以后再说"＝一定会忘**——实测就是这么涨到 4 倍上限的 |

⚠ ⚠ **轮转 ≠ 删除**：整份**先逐字节归档**（`archive/<日期>-<名>/`，**R-17：先落地旧版、再写引用**），
⚠ **再**按主题切进 `volumes/context/`，⚠ 并**同批产出「移出行 → 槽位」逐行对照表**（否则读者找不到搬去哪了）。
⚠ ⛔ **原文一字不改** —— 那是**记录类文本**（改它就是伪造历史）。

⚠ **为什么把这条写进"初始化清单"**：因为**它必须在开账本时就知道**，
⚠ 而**事后补救的代价是"整个项目期间的主持人都在半盲工作"**（实测如此）。

#### 3.2.2 ⚠ ⚠ **会增长的表 / 文档** —— 建立的那一刻就要写明「到顶怎么办」（**2026-10-15 实测教训**）

⚠ ⚠ **本节与 §3.2.1 是两节，⛔ 不是同一件事的两种说法**（⚠ 边界见本节末）。

**陷阱长什么样**：一张表 / 一份文档，**它的行数或字节数随"又发生了一次同类事件"而单调增加** ——
⚠ 例：**每轮一行** · **每立一条纪律一行** · **每次归档一行** · **每踩一个坑一行** · **每条决策一行** · **每个旧版一份**。
⚠ 这类东西**本身不是错**（账本就是要记账）；⚠ **错在"只进不出、且没有到顶动作"** ——
⚠ 它与 §3.2.1 那个坑的**共同末端**是同一个：**住在一份必须一次读完的文件里（上限 64KB）⇒ 增长必然撞上限**。

**实测代价**（本项目真机读数，⛔ 不是推测）：
⚠ ⚠ **同一个缺陷类出过三次**（从轮次表滚出的行**没有槽位**）—— 前两次的修法都是"**补回去 + 写成规矩**"，**两次都复发**。
⚠ 根因**不是"忘了"**：⚠ **那张表一轮加一行，而它住在一份每轮被整份重写、且必须一次读完的文件里**
⇒ ⚠ **增长必然撞上限** ⇒ ⚠ **"裁掉几行"成为一个随时可用的动作，而没有任何东西会在那一刻拦住它** ——
⚠ **写在文档里的规矩拦不住一次写入**。
⚠ 并且**代价已经量到**：⚠ 该类缺陷留下过一个**真实的冗余** —— 在"一轮一文件"改载体之后，
⚠ **正本里那张表仍留着，直到有人再去核它**；⚠ 而骨架侧最紧的一份文件的**余量一度只剩 167 字节**
（⚠ 实测：`65369 / 65536`），⚠ **即再写一条纪律就会越界**。

**⇒ 建表 / 写文档时的三条硬口径**：

| # | 口径 | 判据（可当场跑） |
|---|---|---|
| **1** | **先判它会不会增长**（⚠ 口径：**行数 / 字节数随同类事件单调增加**） | ⚠ 会 ⇒ **本轮就必须写明"到顶怎么办"**，⛔ 不许留"以后再说"（⚠ **"以后"不会自己来**；⚠ 本条要防的正是它） |
| **2** | **到顶动作按表的性质选**（⚠ ⛔ **不许同一句抄 N 遍**） | 见下表 —— ⚠ **每一项都必须写"谁执行"** |
| **3** | **能派生就别手抄** | 内容与 `git log` / 既有文件重复的表 ⇒ **改成一条命令 + 口径式读数**（⚠ 手抄的必然过期） |

⚠ ⚠ **可选动作与适用形状**（⚠ 照搬本项目已跑通的那些，⛔ 不是空想）：

| 动作 | 什么形状适用 | 谁执行 |
|---|---|---|
| **另起一册**（⚠ **写明旧册在哪、指针在哪**） | 纯追加、条目彼此独立 | `未机器化`（⚠ 靠人读指针） |
| **一轮 / 一条一个文件**（⚠ **本轮已在本项目落地**） | 同上，且单条较长 | `check:rounds`（⚠ 有收尾对账钉住"只增不减"） |
| **派生**（能从 `git log` 等算出就不手抄） | 与既有来源重复的表 | 看具体派生命令 |
| **滚动窗口**（⚠ **必须先归档再截**，照 **R-17：先落地旧版、再写引用**） | 只有近期有意义、旧的只作档案 | `check:archive` |
| **分区**（按类别 / 按日期分文件） | 一张表混了多种类别 | `check:archive` |

⚠ ⚠ **"整块搬走"也是到顶动作之一，且它有一条硬判据**（⚠ 本项目实测过）：⚠ **搬走的块必须逐字节一致**
（`cmp` 无输出）· ⚠ **留指针**（写明搬到哪）· ⚠ **⛔ 不是裁行**（裁掉的必须搬进槽位）。
⚠ ⚠ **搬之前先核靶点**：⚠ **在 `scripts/**` 全库实测有没有机检钉在你搬的那一段上** ——
⚠ **本项目实测过**：整节移走一节正本 ⇒ `check:gitignore` **当红**；⚠ 也实测过"新增件忘了登记进 MUST-TRACK 清单 ⇒ 当场红"。

### 3.4 ⚠ 派实施活之前 · 先核目标会话的**预设列**

> **一句话**：**"在跑" ≠ "在干活"** —— 派实施活之前，先看目标会话的**预设**是谁。

| 要做的事 | 怎么做 |
|---|---|
| **看目标预设** | 派活工具列会话时**会给出预设列**（如 `预设=Hob` / `预设=standard`）—— **先看它，再派** |
| **判"能不能施工"** | ⚠ **规划侧/主持预设不能施工**：它只规划、没有 shell、白名单不含写文件工具 ⇒ 派实施活给它 = **永远没有产出** |
| **看编排状态** | 「在等回传」每行**显示目标预设**；若标了**规划侧预设·不能施工** ⇒ **别等**，换一个能施工的会话重派 |
| **建新席时** | 建会话时**显式点名实施预设**（如 `standard`）—— ⛔ 别指望"不填就走实施侧"：不填走的是**配置/出厂默认** |

⚠ **症状极具欺骗性**：编排状态显示「**已开跑**」、会话列表显示 `running`，
**但永远没有产出** —— 因为那个会话按**自己的规矩**（先规划、不动手）干活，**没违规、只是不施工**。
⇒ **判据**：**只看"在不在跑"会漏掉它**，必须看**预设列**。

⚠ **派活工具已自带预警**（第 129 轮起）：给一个**规划侧预设**的会话发消息时，
返回值里会带 `presetNotice`，说明**后果**（不能施工 / 看在跑永远没产出）与**下一步**（换会话 / 显式点名）。
⇒ **读到 `presetNotice` 就照它说的做**，⛔ 不要继续等那一轮的产出。
⚠ 它**只提示、不拦**（给规划侧会话发消息本身可能是合法的，比如问它状态）。
