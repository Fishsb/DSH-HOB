## 一、这一轮解决的是什么

**产品主承诺（闭环派活）在真机上的失败**：执行会话跑完，**回执不会自动回来**；用户点开 Hob 之后才收到。
⚠ 而**执行会话跑完时，派活方通常正是不被打开的那一个** ⇒ 这不是边缘场景，是**最常见的场景**。

## 二、根因（判定 A，证据链完整）

| # | 事实 | 位置 |
|---|---|---|
| 1 | `agents.get(id)` 只是查**进程内内存 Map**：`return this.store.get(id)?.agent` | `dsh-agent/lib/index.js:592-598` |
| 2 | 该表**只有 `agents.enter` 一个插入口**，唯一调用者是 agent loop 的发布路径 | `dsh-agent/lib/index.js:512` · `dsh-agent-loop/lib/index.js:1791` |
| 3 | **冷会话不进表** —— 必须被 `resolveAgent` 显式 resume | `dsh-api-session-controller/lib/index.js:222-230` |
| 4 | `list()` 注释原文：**"without activating an Agent"** ⇒ **能看到 ≠ 是活的** | 同文件 `:1955-1964` |
| 5 | 本仓投递检查踩在这条上：`agent === undefined` ⇒ **直接拒绝** | `src/modules/bus.ts:645-653` |

⇒ **串联**：没点开 ⇒ 不在内存表 ⇒ 投递被拒 ⇒ 点开触发 resume ⇒ 变活 ⇒ 同一份投递才成功。**与用户实测逐字吻合。**

## 三、修法

**一句话**：`deliverImpl` 的 ①分支在 `agents.get` 查不到时**不再直接拒**，改为
**先经宿主原生 `sessionController.resolveAgent(id)` 叫活一次 → 再查一次 → 查到就继续投、查不到才拒**，
且**话术把"叫不醒"与"目标不存在"分开**；`sessionController` 缺席时退化成"明说能力不可用"，⛔ 不假装成功。

**为什么用 `resolveAgent` 而不是自己拼 resume**：它内部"先查 live、再 resume、并发去重"⇒ **天然幂等**。

**四条硬边界（守住，逐条有断言）**：

| 不许动 | 守住的方式 |
|---|---|
| 「拒投给自己」守卫 | `SI-6`：自投仍拒 · **唤醒 0 次**；反向对拍 `SI-v` 摘守卫 ⇒ 自投被唤醒并投进自己 |
| 归档会话拒绝 | `SI-5`：归档仍拒 · **唤醒 0 次**；反向对拍 `SI-z` 摘检查 ⇒ **归档会话被唤醒并投成功** |
| `D4`「至多投一次」 | 本次只改"投之前先叫人起来"，**没动**"投过之后能不能再投" |
| **不许无限唤醒** | `wakeTarget` **只叫这一个 id、一次、有 8 秒上限** |
| **活目标不许变慢** | `SI-4`：活目标 `ok=true` · **无 `wake` 字段** · **唤醒 0 次**；反向对拍 `SI-w` 改无条件唤醒 ⇒ 活目标被叫 1 次 |
