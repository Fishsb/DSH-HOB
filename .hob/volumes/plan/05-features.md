### 5. 功能说明

### 5.1 用户视角的完整链路

**共同入口（⛔ 不许跳过）**：接到用户会话 ⇒ **先对照当前需求、现行方案、当前状态** ⇒
理解意图与边界，并**辨认这是"现行规划内"还是"新功能需求"**。
⚠ **首读的是 `REQUIREMENTS.md`（当前功能需求）与 `PROJECT.md`（现行方案）** —— 二者缺一即不许开工。

**A · 现行规划内推进**（需求没变）：定位当前阶段 → 技术方案与**事前**验收标准 →
拆分排序、指定实施会话交接 → 核对原始证据 → **验收或退回** → 更新当前账本。

**B · 新需求先干净重构方案**（用户目标与现行方案**冲突**）：
确认用户真实功能目标与取舍 → **更新当前需求**（`REQUIREMENTS.md` 与其卷）→
**把方案整体重构**成只描述现状的版本（旧版**逐字节归档**，⛔ 无补丁式历史说明）→
然后并入 A 的后半段（技术方案 / 标准 / 交接 / 核证 / 验收或退回 / 账本更新）。
⚠ **更新需求 ≠ 实施已完成**；⚠ **方案变更须用户批准**；⚠ **执行回报不构成验收**。

**分发有两条路**：目标会话**活着**时 Hob **自己投递**；没有活会话（或用户指定要自己搬）时**照旧手工转达**。

```
① 用户新建会话，选 **Hob**（规划侧）
② 用户对 Hob 说人话表述意图（**沟通与理解需求发生在这里**）
③ 先照上面「共同入口」对照当前需求与方案，判是 A 还是 B（B 先走需求+方案重构，再回到这里）
④ Hob **拆分任务、编排任务**（定先后与依赖），产出「给实施会话的指令」+「给你的白话」
⑤ **分发（两条路）**：活会话在 ⇒ Hob 列候选、**与你确认目标**后把**自带要点的指令**投过去；
   没有活会话 ⇒ 用户把**指令**（或它的路径）粘到实施会话（手工路，仍是默认降级路径）
   ⚠ **要点必须在消息正文里**，不能只给一个路径 —— 交接区在工作区之外，执行方可能读不到
⑥ **实施会话执行落实**：**按消息正文的要点执行**，在工作区把指令做掉
   （**中途不弹窗问人**），完成后把**回报交回**（**固定六段**）
⑦ **Hob 监督验收落实情况**（**只认原始读数**；核不到就写"未验证"），
   并**逐条接住**回报里的「待决问题」
```

**并行分支（§4.5）**：要推进的几件事**互不影响**时，④ 之后走**隔离路** ——
Hob 派会话**建卡**（各带 `isolation:"worktree"` + 执行侧预设）⇒ **看板到点自动点火**、
各在自己的 `git worktree` 里干活 ⇒ Hob **只读回收**、汇总 ⇒ **派会话合并**回主干。
⚠ 这一路上 **Hob 自己不建卡、不合并**；它也**不因此多出任何工具**。

⚠ **投递 ≠ 执行**：`hob_send` 只把一条消息送进目标会话的队列，**不代表活干了**。
契约明写 `Delivering is not doing` —— Hob **不得**声称自己"已实现 / 已改好 / 已完成"。
⚠ **建会话 ≠ 委派**：`hob_spawn` 建出来的是**空会话**，得投递才开跑。
⚠ **回传 ≠ 验收**：回传只是"**对方说它做了什么**"。
⚠ **"写了交接文件" ≠ "派出去了"**（CHG-027）：这是**两个独立动作**，**中间没有耦合**。
⇒ 系统为此**单记一份"待投递"中间态**：写了交接文件 / 建了会话 ⇒ **记一条**；投递成功 ⇒ **清掉**；
状态查询**报出待投递项**（**空态也给读数**）。理由：此前**"写了但没投"在系统里根本不存在** ⇒ 漏派**静默**。

⚠ **目标会话由人指定，不自动挑**：Hob 列出候选、**问用户**（或按用户明确给的目标）投递；**不按工作区/活跃度自己猜**。
⚠ **投递前先看「侧=」**（2026-10-17 · CHG-058）：**只往实施侧投实质活** ——
⚠ **投给规划侧 = 那个会话只会再规划一次**（它无 `write` / 无 `bash`）。

⚠ **仍未做的**：**跨系统通信（M6b）** —— ⚠ **暂缓、无实现**（见 §3.2）·
**Hob 自己**改动看板状态（并行推进时**由被派的会话建卡**，见 §4.5）· 自动挑目标会话。

⚠ **创建 Hob 会话的弹窗（目标形态）**：**每个新建 Hob 会话**应在创建前弹一次对话框，
**分别**选 **可读范围** 与 **推进项目的工作方式**，两个选择**归属该会话并持久化**；
**取消不建会话**；**无交互入口**必须显式给两项，否则**拒绝并给可读原因**；**普通实施会话不弹此窗**。
⚠ 该弹窗应在**该会话的首条回应发出之前**出现，不需要用户先点某个入口；
⚠ 用户取消或未选择时，该会话**保持最低档且不推进**，并以可见提示告知；⚠ **不删除会话**，也不静默当作已选。
⚠ **实现进度与加载状态见 `CONTEXT.md` §2.1b**（⛔ 本节不记进度状态）。
⚠ **新建会话的读范围只开放最低档**：**只可选「账本权限」**，另两档**照常呈现但不可选**
（灰显 + 标「暂未开放」），**待宿主持久清理能力具备后再开放**；推进方式三档**不受此限**。
⚠ 判据是 `check:hob-create` / `check:hob-create-dom` / `check:hob-gate` **三族**
（策略面另有 `check:policy`）；⚠ **真机渲染 / 真实宿主归档 / 真机 dispose 均未验**。
⚠ **设置面板的两个全局控件已下线**（不再渲染），这两项的选择已移到本弹窗；
实现与验证状态、剩余工作见 `CONTEXT.md` §2。⛔ **不许把目标写成"已生效"**。

⚠ **一单一执行方 —— 派单认领（防"两个会话同跑同一单"）**：
**同一个交接目录 + 同一工作区**两件事叠加时，**两个会话可能同时认领同一单**
（实测踩过：两个会话读同一份 `TASK.md`、做了同样的改动，靠"文件 mtime 变了"才**事后**觉察）。
⇒ 约定：**派单方在 `TASK.md` 顶部写一行 `claim: <session-id> <ISO 时间>`**；
**执行方开工先读该行** —— **已被他人认领就停手上报，不接管、不覆盖**。
该行由**派单方**落，执行方不自行改写；模板见 `.hob/templates/TASK.md` 顶部。

### 5.2 工具

**只有规划预设挂本插件的工具**；实施侧用**宿主原生工具**。

| 工具 | 干什么 | 约束 |
|---|---|---|
| `read_contracts` | 读**账本区**内的 `.md` | 只读；单文件有上限（超限**截断并标注**）；路径校验；**拒软链** |
| `write_hob` | 写**账本区**（正本 + `volumes/<卷>/*.md` + `archive/<日期>-<名>/*.md`） | 骨架只读；有备份、有干跑、有**缩水守卫**；越界与软链一律拒；⚠ **落盘前做三件事：核具名引用（①）· 渲染读数标记（④）· 写成功时可一步投出（②）**；⚠ **写交接文件时，返回消息尾部追加一句「尚未投递」提醒**（**提示，非闸门**） |
| `hob_sessions` | **列本实例可投递的活会话**，⚠ **每行报出「侧=」**（**规划侧 / 实施侧**） | 只读；**归档会话不列**；⚠ **「侧」与「预设」取自宿主 `agentPreset` 投影**（⚠ 与宿主自己的读法同源；⛔ **不是建档头** —— 建后改过预设的会话，建档头**不会再变**）；⚠ **投影读不到时走降级路径**：列表**置顶声明** + 每行标注「降级」 |
| `hob_send` | **把一条指令投递给指定会话** | 目标须是活会话；拒投给自己；**投递归档会话会被明确拒绝**；**投递 ≠ 执行**；投递成功 ⇒ **清掉匹配的"待投递"记录** |
| `hob_workspaces` | **列已登记的工作区** | 只读；只列**已登记**的（没登记过的建不出会话） |
| `hob_spawn` | **新建会话并强制归属到工作区** | **不接受"不指定"**：显式给 → 或落到本会话工作区 → **解析不出就拒**；**绝不造孤儿**；⚠ **有归属 ≠ 用户看得见** —— 空白会话**被宿主有意从列表过滤** ⇒ **建完不投递，用户看不见它**；**并记一条"待投递"** |
| `hob_dispatch` | **派活并登记回传**：投递后**等它跑完自动把结果送回** | 目标须是活会话；拒派给自己；**停了直接拒绝**；**回传 ≠ 验收**；投递成功 ⇒ **清掉匹配的"待投递"记录** |
| `hob_orch_status` | 看编排状态：是否已停 / 在等哪些会话 / 回传过几次 / **待投递几份** | 只读；是**派活方自己的记录**，不是对方进度。⚠ **"待投递"必须报空态**—— **让"没有漏"也是可读的**；⚠ **「预设=」那一列与派单判定同源（宿主投影，单点实现）**，降级时行内标出 |
| `hob_orch_control` | **停 / 恢复自动回传（刹车）** | `stop` 后不再回传、也不再接受新派发；**用户的话优先** |

⚠ ⚠ **为什么 `hob_sessions` 必须有「侧=」**（**2026-10-17 · CHG-058**）：**把实施活派给规划侧的会话 ⇒ 它只会再规划一次**
（**它无 `write` / 无 `bash`**）—— ⚠ 而这是**静默失败**：它在列表里**看着和别的会话一样**。
⚠ ⚠ **实测依据**：**旧读法读的是建档头**（`session.header.agentPreset`）⇒ **8 条会话里 3 条被判错**
（⚠ **含 Hob 自身那条** —— 那些会话是在**建后的空白窗口内**才改成 `Hob` 的，⚠ 而建档头永远停在 `standard`）。
⇒ ⚠ **口径**：**一律照宿主的读法**（`agentPreset` 投影）；⛔ **不许用部署默认顶替**、⛔ **不许用列表自身的预设顶替**。
⚠ ⚠ **同一条读法已覆盖到 `hob_orch_status`**（**2026-10-17**）：那一列的预设读数**与派单判定同源、单点实现**，
降级时行内标注 —— ⛔ **不许在第二处再写一份读法**（本仓纪律：同一判据写两遍必然漂移）。

**前两个工具是 Hob 能维护自己文档的唯一手段**（用户要求：权限尽可能收敛，但 Hob 需要维护自己的文档）。
**其余是会话总线与编排的能力**（用户明确要求"推进自动派发"，方案 B：自建会话总线，不依赖外部插件）。

⚠ **名单与条数一律不写死**（**会静默漂移**）⇒ **读 `src/preset/tools.ts` 的注册表实测**。
⚠ ⚠ **并行隔离推进（§4.5）不在此表里加一行**：它**不引入新工具** ——
隔离执行走的是**宿主看板既有的通道**，Hob 用它**已在白名单里的只读工具**回收结果。

**⚠ 四个自注册的读工具（2026-10-14 · CHG-057）**：`hob_read_doc` · `hob_glob` · `hob_grep` · `hob_read_image` ——
它们是**可读权限控制的落点**：**账本权限档下不在模型面**，文档权限 / 完全权限才发到模型。
⚠ **它们在注册面恒存在**（那是"改完即生效、不必重启"的代价，见 §4.3 / §7.2）；
⚠ 名字带 `hob_` 前缀是**必须的** —— 宿主已注册了同义的裸名（`read` / `glob` / `grep` / `read_image`），
重名会撞车（**实测**）。
⚠ 它们**只读**：路径校验 + **拒软链** + 档位规则（**文档权限**只放行 `.md`；**完全权限**放行任意文件）由**单调执行哨兵**兜底。
⚠ ⚠ **「完全权限」只放宽可读范围**：**完全权限 = 工作区里任何文件都可读，仍然不能写、不能执行命令、不能组队。**

#### 5.2.1 `write_hob` 的三条结构改造行为（① 引用校验 · ② 写入即投递 · ④ 读数渲染）

> 总纲：**把检查从"事后、别处、他人"，搬到"事前、当场、自己"**（CHG-029 · UD-91）。
> 三条都发生在**写入那一刻**，且**都只提示、不拒写**（工具语义仍是"按你给的路径与内容如实写"）。

**① 写入边界校验**：落盘前扫**具名引用**（`archive/<日期>-<名>/…` 路径 · `TASK-R<n>….md` 文件名），
**指不到实体的逐条点名**（含**第几行**）。⚠ **只提示、不拒写** —— 因为**它必然会咬到"复述探针结果"这类元讨论**。
⚠ 形如 `archive/<日期>-<名>/`、`TASK-R*.md` 的**占位 / 示意 / 通配**形态**按设计不计**。

**② 写入即投递**：

| 参数 | 行为 |
|---|---|
| **目标会话 id** | 给了 ⇒ **写完即投**（走 `hob_dispatch` **同一条路径**）；返回里含**投递结果**与**投递后读数** |
| **转达标注** | 标记"这是**有意人工转达**" ⇒ 状态行**分开报** |
| **都不给** | **照写**（⛔ **不做硬闸门**） |
| **两个同给** | **以真投为准** |

⚠ **目标仍由人指定**；⚠ **清"待投递"的保守方向 = 宁可少清**。

**④ 读数渲染**：**会漂移的读数不再手抄**，改由写入工具在落盘前渲染。
**取值判据三条**：**不依赖正在写的那个文件** · **落盘后仍成立** · **稳定**（同输入 ⇒ 同值）。
**语法**（⚠ **示例一律放围栏 / 行内代码段内** —— 裸写会被渲染器吃掉，那是设计）：

```
<!-- hob:count | <相对账本根的目录路径> -->   → 该目录的条目数
<!-- hob:bytes | <相对账本根的文件路径> -->   → 该文件的字节数
```

| 项 | 口径 |
|---|---|
| **可渲染** | **账本区内**的**文件字节数** · **目录条目数**（目标是**相对账本根**的路径） |
| **不可渲染** | **工作区里的事实** · **两仓 HEAD**（必被随后的提交作废） |
| **结构性拒绝**（⛔ 不靠人记） | 目标 **== 正在写的那个文件** 或 **== 它的父目录** ⇒ **拒绝渲染并点名**；另有同向拒绝：目标不存在 / 种类不符 / 越出账本根 / 含软链。⚠ **目标不存在时拒绝渲染 0** |
| **豁免两类** | **① 围栏代码块内** · **② 行内代码段内**。⛔ **裸写的标记一律被咬**。⚠ **"豁免"只管渲染器与收尾断言，不等于"引用安全"** |
| **不可逆** | 落盘的是**实值** ⇒ **重写正本时须把值写回标记形态**（⚠ **这是靠人记的一环** —— 已知缺口） |
| **兜底** | 收尾机检扫正本里是否有**未渲染的标记** ⇒ 有即 **FAIL**；并配**自带样本**（两侧都验） |
| **判据** | **看返回值里有没有"读数渲染"那一行**，**不看产物戳** |

> ⚠ **为什么"渲染"要在插件里做、而不是让执行方回填**（**写账本的一侧 / 执行的一侧**约束）：
> **执行方**可能与**写账本的一侧**不在同一处（另一个实例 / 另一台机器），
> **账本区路径根本不可达**，回填这条路到那时必然断掉；而**"执行方报值、Hob 填"只是把二手读数换个人手写**。
> ⇒ 采用**"谁写账本，值就在谁那里取"**：插件代码本身跑在**宿主 Node 进程**里、**本来就有 `fs` 能力**
> ⇒ **不需跑命令、不开任何新写口**，账本仍**只有 Hob 侧一个写者**（*Single Writer Principle*）。

**⚠ 工具面有三层，别混为一谈**

| 层 | 含义 | 判据（谁在断言） |
|---|---|---|
| **注册面** | 该预设作用域里**注册了**哪些名字 | `ctx.tools.view(scope).knownNames` |
| **模型面** | **发给模型的**那一份清单（= 装配期白名单过滤的结果） | `MODEL_TOOL_ALLOWLIST`（**按档位取**）；机检钉住 |
| **执行面** | 真调能不能落地 | 白名单内可落地；名单外被拒（`TOOL_NOT_ALLOWED`） |

⚠ ⚠ **能力落点 = 「声明面 与 白名单 的与门」**：只换声明面不增能力、只扩白名单得 `unknown tool`，**两件一起才可达**。
⚠ **白名单的粒度 = 工具名**：它**不能**用来闸"写到哪个路径 / 写什么类型"。
⚠ **"注册面存在"不等于"拿得到"**：挂 `tool-fs` 后 `write` / `edit` 会落到**注册面**，但它们**不在**白名单
⇒ 模型面看不见、执行前拦截也拒。⚠ **但那是收敛措施、不是安全边界**（拦截器 **fail-open**）—— **已知残余风险**。
⚠ **同一句话也适用于四个读工具**：它们**在注册面恒存在**，而**账本权限档下不在模型面** ⇒ 同样读作"不可达"，⛔ 不是"物理不存在"。
⚠ **插件不注册宿主原生的 `read` / `bash` / `write`** —— 权限边界靠"工具面"实现。
⚠ **skill 收窄态**：`includeDefaultRoots: false` + 空 `customSkillDirs` ⇒ `~/.dsh/skills/` 那批**全部不可见**；
那是**有意的收窄态**，**不是故障**。

**设计约束**：每个工具**只做一件事** · 守卫逻辑**只写一份**（"守卫写两遍必然漂移"）·
危险操作要有**干跑**与**备份**。
**⚠ 名单与条数以实测为准**（模型面白名单的名数由 `check:presets` 的判定钉住）。

### 5.3 设置（M4 + C1）

- 走**原生 configForms**（宿主设置界面，不自建）
- **字段必须在设置页可见** —— 否则用户看不到、也**不报错**（静默失败）
- **分区标题 = `dsh-hob`**
- **模块开关全部显示**
- **可读权限控制控件（2026-10-14 · CHG-057；2026-10-17 改名 · CHG-059）**：三档
  **账本权限 / 文档权限 / 完全权限**，
  与「新建会话默认」卡片同形态（**分段控件** —— 宿主没有滑块原语，⚠ **这是如实取舍、不是遗漏**）；
  ⚠ **改完即生效**（走 volatile，见 §7.2）—— **界面上要写明这一点**，否则用户会以为要重启。
  ⚠ **两个全局控件已下线**（不再渲染）：`PermissionCard` / `WorkModeCard` 已不挂在设置页上，
  只留一句"移到新建弹窗"的只读提示；⚠ **选择已移到新建 Hob 会话的弹窗**（见 §5.1）。
  ⚠ **配置字段保留**（旧会话迁移的取值来源），⛔ **不许把"控件下线"读成"配置也没了"**。
  ⚠ ⚠ **选中「完全权限」时，界面必须紧邻显示那句限定**：
  **完全权限 = 工作区里任何文件都可读，仍然不能写、不能执行命令、不能组队。**
  （名字里带"完全"两字，只给名字不给边界，读者会把"读得更多"读成"权限更大" —— **R-26**。）
- **「新建会话默认」卡片**：四个字段（预设 / 模型 / 供应商 / 推理强度），
  **只影响本插件建出的会话**（`hob_spawn`），四字段留空 = 交还宿主默认。
  ⚠ 预设下拉的候选**排除规划侧预设**，**出厂默认 = 标准模式**。

> ⚠ **为什么规划侧预设不作候选**：`Hob` 无 `bash` / `write` ⇒ 拿它当默认预设，
> 建出的会话**只会再规划一次**（死循环）⇒ 候选**排除**该 id（**可见说明，不静默过滤**），
> 且**空值一律按标准模式** —— **显示与派活同源**（同一个常量），**不再去问宿主的全局默认**。
> ⚠ ⚠ **同一条道理适用于并行隔离推进**：建卡时的**执行预设必须显式指定**，
> ⚠ **缺省会落到部署默认**（本机 = 规划侧）⇒ 执行会话**干不了活**（§4.5 / R-20）。

**⚠ 设置面四条硬规则**（⚠ **机制细节、实测过程与反例见经验库**；此处只留结论）：

| # | 规则 |
|---|---|
| **1** | **volatile 写法**：**父对象不标 + 要显示的字段各自标** ⇒ 未标的子字段**被滤掉**（**能隐藏**）。⚠ **抛错的是「父子同标」，不是「给子字段各标」**。⛔ **禁用**"父整体 volatile + schema 不声明某子字段" —— 它能隐藏，但会**静默抹掉那个字段的值** |
| **2** | **volatile 对象的读取**：运行时是**只读 ref**，直接读**静默得到 `undefined`**（ref 本身恒 truthy）⇒ 必须用**收口函数**统一解出普通对象，**不许在各处直接读** |
| **3** | **`describe().value` 是投影视图，不是原始 config** ⇒ 用它判"某个配置键是否还在"会**得到错误的结论**。**正确判据**：判"键是否保留"用 `--dump-config` 或运行时 `fiber.config`；判"设置页显示哪些"用 `describe()`；判"最终渲染出什么"**只能真喂数据看输出** —— ⛔ **不许用 `grep 产物`** |
| **4** | **验证"某配置键是否还在"时，测值不要用默认值** —— 用默认值时，"**保住了**"与"**被抹掉后由默认值补回**"**读数完全一样** |

**⚠ 生效性必须按"半边"分别判断**：

| 改动所在 | 生效方式 |
|---|---|
| **client 半边** | ✅ **有 HMR** ⇒ **刷新浏览器即可** |
| **host 半边** | ❌ **无 HMR** ⇒ **必须重载/重启** |
| **bundle patch**（本包的 `cordis.patch.yml` 与 `preset/*.patch.yml`） | ❌ **不在 HMR 监视列表内** ⇒ **必须重载/重启** |
| **profile 层 patch** | ✅ **在** HMR 的 `watchConfig` 列表内 |
| **volatile 配置值**（`permission.level` / `spawn.*`） | ✅ **改完即生效**（值型 ⇒ 逐 step 现算）—— ⚠ **与上表不冲突**：上表管**代码与声明**，本条管**值** |

⚠ **两层结论相反、各自成立**，别把一条推广到另一条。
⚠ **`--dump-config` 是离线读盘，与运行进程的内存无关** —— 它显示新值**不等于**进程已生效。
判断"是否已生效"要**看行为读数**（**新代码独有的字样是否出现** + **只有重启才会变的计数是否变化**），
⛔ **不能只看产物指纹文件**（它只证明"构建过"，不证明"加载了"）。
⚠ **这条说明要出现在用户可见的界面上**，不能只写在代码注释里。

**面板另有三条实测纪律**（来自真机报障，**过程见经验库**）：
① **渲染值必须来自宿主 form 的外部存储**，且**订阅宿主 form 自身** —— 否则写入成功、下拉框仍显示旧值；
② **预设名与 DSH 一致**：内置预设在 DSH 里显示**本地化名** ⇒ **复用宿主词条** + **自备兜底**，
且**绝不显示内部键名**（宿主取不到时**返回键名本身**，必须判成"没取到"）；
③ **面板跟随语言**：注册**中英词典**（两份**键集一致**，机检钉住）+ 订阅语言服务。
⚠ **已知限制**：`src/config.ts` 的字段说明**仍是中文**（由宿主**插件管理页的自动表单**直接显示，
那条路径**没有**语言机制）。
