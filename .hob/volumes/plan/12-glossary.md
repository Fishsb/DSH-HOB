### 12. 术语表

⚠ **只列本项目专有、或易混的术语**；通用机制词与更细口径见 §4–§10 与经验库。

| 术语 | 含义 |
|---|---|
| **本插件 / dsh-hob** | 装在 profile 内的 DSH 插件（不是独立实例） |
| **Hob** | 本插件自带的**规划侧预设**：与用户沟通、理解需求、**拆分 / 编排 / 分发任务、监督验收**；出指令、维护文档；**只读的事自己直接做**；**能做的是投递与建会话** —— **但"投递"不是"执行"**、**"建会话"不是"委派"**；**改动的活仍不做**；**决策自主、可向用户提问**；⚠ **读的范围按可读权限控制可调**（见「可读权限控制」条，§4.3 / §6.1） |
| **可读权限控制（`permission.level`）** | 设置里的那一组开关（**2026-10-17 由「权限档位」改名 · CHG-059 / UD-133**）：三档显示名 **账本权限**（缺省）· **文档权限** · **完全权限**，配置值分别是 `ledger` / `project` / `workspace`。⚠ **只改「读到哪里」** —— 账本权限档**看不到**工作区文件 · 文档权限档另可读工作区 **`.md`** · 完全权限档另可读**任意文件**（含代码与图片）+ 列文件 + 跨文件搜索。⛔ **任何一档都无写、无命令、无组队**（写边界三档一致）；⚠ **改档位即时生效**（volatile 值型），⛔ 不必重启；⚠ **代价**：四个读工具**在注册面恒存在**（账本权限档下只**不在模型面**）—— 这是"不重启即可换档"的**必然代价** |
| **「完全权限」的边界句** | 这个名字**只描述"可读范围最宽"**，⛔ 不表示权限更大：**完全权限 = 工作区里任何文件都可读，仍然不能写、不能执行命令、不能组队。** ⚠ 凡用户可见处出现该名，**紧邻必须有这句**（`R-26`） |
| **职责边界** | **预设必须自带的一块正文**：**做什么 / 不做什么 / 责任止于何处（三条不变量）/ 这条边界靠什么守住**（并**如实声明它是不是安全边界**）。⚠ **正文载体 = 预设契约**（人读版 + 机器读版**逐字一致**）；**方案只留对照与指针**；由 `check:presets` 的 **⑤k** 钉住（见 §4.3 / §10.5） |
| **包名 / 内部标识** | `dsh-hob` —— 插件包名，同时是目录名、loader 行 id 前缀、模块子路径前缀、设置分区标题；**与预设 id 无关**（⛔ 不印给用户）。⚠ **三档的配置值（`ledger` / `project` / `workspace`）同属内部标识**：进配置与代码，⛔ 不进对话文本 |
| **投递 / 建会话 / 回传** | 三件事**三条口径**：**投递 ≠ 执行** · **建会话 ≠ 委派** · **回传 ≠ 验收** |
| **闭环派活** | 投递 → 等对方跑完 → **结果自动回到派活方** → 判断续用还是新建 → 再派下一步 |
| **并行隔离推进** | **互相不影响的几件事同时推进**：每件事各占一个**隔离单元**（看板卡 + 独立 `git worktree` + 独立分支），**互不打架**。Hob **拆分 → 只读回收 → 汇总 → 派会话合并 → 验收**；**建卡与合并都在被派的一方**（见 §4.5） |
| **隔离单元** | 一次并行推进里**一件事**的独立工作场：看板卡 + 该卡的 `git worktree` 目录 + 它的分支（`task/<标题>+<taskId>`） |
| **执行预设** | **建卡时逐卡指定**的、给执行会话用的预设。⚠ **必须显式给执行侧**（可写）的那个 —— **缺省会落到部署默认**，本机即**规划侧** ⇒ 干不了活（**R-20**） |
| **外部会话同步** | 宿主看板的行为：**把本项目每个会话自动记成一张卡**（标题是用户消息首行、`prompt` 空、`isolation:"none"`）。⚠ **认出它、别当成有人故意建卡；删了会回来**（**R-21**） |
| **待投递** | **写了交接文件 / 建了会话，但还没投出去**的中间态 —— 单记一份运行态记录，**投递成功即清**；状态查询**报出它（含空态）**。⚠ **"写了文件" ≠ "派出去了"** |
| **写入即投递 / 写入边界校验 / 读数渲染** | `write_hob` 落盘那一刻的三条行为（**§5.2.1**）：写完可即投（含"有意转达"标注）· 当场核具名引用（只提示不拒写）· 把会漂移的读数渲染成实值 |
| **刹车** | 停 / 恢复自动回传的开关。**闸门建在回传之前**；**用户的话优先** |
| **分发** | **要点随消息走**：把**可独立执行的要点**写进**投递的消息正文**，完整长文另落交接区。**两条路**：活会话在 ⇒ Hob **直接投递**（目标由人指定）；否则**用户手工转达** |
| **只读直接做** | **只读的活 Hob 自己直接做**，**不转给实施会话**；要动手改东西的活仍一律转出。判据 = 「有没有**改动**能力」（⚠ **不是**「有没有工具」—— 后者会随能力扩展而失实） |
| **与门（声明面 × 白名单）** | 一项能力要真拿到，**声明面**与**白名单** **两件都要**；⚠ **白名单粒度 = 工具名**，闸不了"写到哪个路径" |
| **决策自主 / 可提问** | **能按项目方案主线判断的，Hob 自己决策并推进**；**只在"只有用户能定"时才问**；**可提问 ≠ 要多问** |
| **方案落点审核** | **用户提出项目改动后的固定三步**：**先审落点 → 落到方案本体 → 整份重构**（见 §10.5）。⚠ **含本项目自身在内**，与其它任务编排任务一致 |
| **先对照方案** | **收到任何输入（用户的话 / 回传 / 提问，不分类别）** ⇒ **Hob 的第一个动作固定为对照方案与账本**（定清"落在方案的哪一步 / 边界 / 判据"）⇒ **再决定下一步**；⛔ 不凭感觉、⛔ 不拿会话记忆当依据。⚠ 与「指令以方案为准」（管**发出去的指令**）与「推进优先」（管**先做哪一件**）**叠加生效**（见 §4.3；UD-112 / CHG-056） |
| **改动不只改自己** | **凡改动都须把账本等相关部分一并考虑** —— ⚠ 理由是**它为了以后协助用户去管理其他项目** ⇒ **可复用层（骨架 / 模板 / 契约 / 判断口径）必须同批跟着走**（见 §10.5） |
| **可复用层（骨架）** | 工作区 `.hob/**` 里**拿去开箱给别的项目**的那几层：`README.md` · `INIT.md` · `templates/` · `roles/` · `drafts/` · 经验库索引 `EXPERIENCE.md`。⚠ **判据**：「**换个工作区开箱，得到的是新规矩还是旧规矩？**」（**UD-103 / CHG-047**）；⚠ **记录层**（`experience/**` 的历史条目）**⛔ 不属于可分发面** —— 它记的是**本项目**的历史 |
| **回报六段** | 结论先行 / 前置读数 / 做了什么（附原始证据）/ **未做到·未验证·与指令不符（不得埋）** / **待决问题** / 建议 |
| **回归对拍** | **把本轮刚修好的东西「注回去」，看新判据红不红**（**2026-10-14 立**）。⚠ 与"注入一个**新造**的违规"不同：后者**测不出"刚修好的东西没人守"** —— 第 148 轮实测：正是它抓出了一条**把刚修净的文件整文件豁免掉**的判据缺陷 |
| **账本区** | `/home/lk/.dsh/hob-ledgers/<工作区名>/` —— **正本在根目录** + `volumes/`（卷：一事一文件）+ `archive/` / `backups/` / `runtime/`。**在工作区之外**，**该目录自己即独立 git 仓** |
| **归档目录名两档（R-16）** | ① **能不能建**：写侧守卫**只接受小写字母 / 数字 / 连字符**；② **认不认得出**：判据**更宽**（宽是为了把不合规写法也认出来报错）。⚠ **两档别混** |
| **骨架 / 经验库** | 骨架 = 工作区 `.hob/` 下的可复用格式契约（**进 git**）；**经验库** = `.hob/EXPERIENCE.md`，**机制细节与教训的唯一来源** |
| **账本可读性（预算）** | ⚠ **每份正本都应能被 `read_contracts` 一次读完**；⚠ **超限 ⇒ 默认路径给的是部分信息** ⇒ **收缩前先把当前整份归档**（**R-17**）；⚠ **整批移出内容时，须同批产出「移出行 → 槽位」逐行对照表**（**CHG-043**） |

**★ 需求与真相分层（2026-10-22 起的第一组术语 —— 它们区分"现行"与"历史"）**

| 术语 | 含义 |
|---|---|
| **当前功能需求** | **用户现在希望项目实现的功能结果及可观察完成条件**。载体：`REQUIREMENTS.md`（根地图）+ `volumes/requirements/REQ-<编号>.md`（条目正文）。⚠ **只写功能与结果** —— 技术手段、一次性实施决定、已结束批次都**不是**功能需求 |
| **当前项目方案** | **这些目标现阶段怎么做**（架构 · 权限 · 接口 · 配置 · 风险）。载体：`PROJECT.md` + `volumes/plan/`。⚠ 正文**不堆修订痕迹** |
| **当前状态** | **正在推进什么、还欠什么、哪里未验、下一个阶段是什么**。载体：`CONTEXT.md`（撞上限时移出到 `volumes/context/`） |
| **旧用户决策（历史）** | 过去用户拍板的**记录**，载体是**卷** `volumes/user-decisions/`（逐条附原话）。⚠ **只读历史、非现行需求**。⚠ 旧的根地图件 `USER-DECISIONS.md` **已退场**（归档在 `archive/2026-10-25-oldroot-retire/`）。⚠ **引用一条旧决策 ≠ 把它变成当前需求** |
| **技术变更史（历史）** | `DECISIONS.md` / `volumes/decisions/` 的 `CHG-nn`：**方案为什么改**。⚠ 其中 §八「现行通用规约」**是现行规约**，条目本身是历史 |
| **逐会话策略** | **目标形态**：每个 Hob 会话自己的"可读范围 + 推进工作方式"两项选择，创建时选定、归属该会话持久化。⚠ 与"全局 `permission.level`"**不是一回事** —— 后者是**过渡期权威**；⚠ **加载与现状见 `CONTEXT.md` §2.1b**；⚠ **新建只开放最低档**（另两档呈现但不可选） |
