### 4. 核心能力

### 4.1 总原则：插件是支撑机制，项目目标是"总工程师闭环"

**先说清主次**（⛔ 别把插件层的比喻当成整个项目目标）：
项目服务的首要目标是 **Hob 作为项目总工程师**，维持项目目标的连续性 ——
理解边界、制定技术方案与事前验收标准、安排实施、独立核对证据后验收或退回、维护项目工作簿（见 §1）。
**插件**是承载这条闭环的宿主内机制；"电话只传话"仍能说明**插件层**的职责，但它不是项目目标本身。

| 谁做 | 做什么 |
|---|---|
| **插件** | 拨号（找会话）、传话（投递消息）、把回来的话显示出来、读写账本、收敛权限、提供创建交互 |
| **Hob 会话**（本插件预设） | **规划与核验发生在这里**：对照当前需求与方案、出技术方案与验收标准、拆分交接、验收或退回 |
| **实施会话** | 按完整指令落实变更、给原始读数与问题；它的回传**不是**验收 |

**翻译在会话里，不在插件里。** 插件不调 LLM、不定义 prompt、不解析模型输出。

**自主与拍板的分界**：用户决定**要实现什么功能、接受什么代价**；Hob 在已批准范围内做**技术判断**
（技术方案、验收标准、执行方、顺序）并**自行为之**，⛔ 不拿文件名 / 测试脚本 / 实现手法去问用户。
⚠ 判据：**"这是产品取舍，还是技术选择？"** —— 答得清就自己定；**只有产品方向、取舍、范围、代价接受度**归用户。

### 4.2 同实例内会话通信（核心能力）

**宿主原生能力，不需要任何自研协议**：

| 能力 | 宿主接口 |
|---|---|
| 列出会话 / 取某个会话 / 取会话的 agent | `sessions.list()` / `sessions.get(id)` / `agents.get(id)` |
| 把消息投进会话 | `agent.followup(msg)` / `steer(msg)` / `inject(msg)` |
| 订阅会话事件 / 看 agent 忙闲 | `session/event` · `agent/status` |

**三种投递语义**：`followup`（排在当前轮之后，独立一轮，**唤醒**）·
`steer`（插进正在跑那一轮的最近 step 边界，**唤醒**）·
`inject`（只写进模型上下文，**不唤醒**）。**默认用 `followup`**。

### 4.3 预设与角色

**本插件自带的预设**（⚠ **名单与条数以 `preset/` 目录与 `check:presets` 实测为准**）：

| 显示名 | id | 基于 |
|---|---|---|
| **`Hob`**（与 id **同字面值**） | `Hob` | DSH **极简模式**（minimal）+ 若干**指名增行** |

**Hob 干什么**：与用户沟通、理解需求，**拆分任务 → 编排任务 → 分发任务 → 监督验收落实情况**；
把活写成给实施会话的指令；**只读的事自己直接做**；**能按项目主线判断的自己决策推进**。

**Hob 的权限面（现行，清单以源码注册表实测为准）**：
- **只读**：**自己的账本** + 网页正文 + 看板与圆桌**只读**查询；**工作区文件按可读权限控制**（见下）
- **只写账本区** · **可向用户提问** · **可加载技能指引** · **可把产出挂成交付卡** · **读工作区 `AGENTS.md`** · **`/compact`**
- **可投递指令到活会话** · **可列工作区并新建会话**（**强制带工作区归属**）
- **仍无**：写工作区 · 无命令 · 无执行 · 无组队

**★ 可读权限控制（`permission.level`，缺省 = 账本权限 · 2026-10-14 · CHG-057；2026-10-17 改名见 CHG-059 / UD-133）**：

| 档位（显示名） | 配置值 | 能读到哪里 | 备注 |
|---|---|---|---|
| **账本权限**（缺省） | `ledger` | **只有账本区** —— ⛔ 看不到工作区文件 | = 上一轮收缩后的行为 |
| **文档权限** | `project` | 账本区 + 工作区里的 **`.md` 文档** | ⛔ 仍读不到代码 |
| **完全权限** | `workspace` | 账本区 + 工作区**任意文件**（含代码与图片）+ 列文件 + 跨文件搜索 | ⛔ **仍不能写** |

⚠ ⚠ **三档的差别只有"能读到哪里"** —— **写边界、命令、组队在三档下完全一致**（都不存在）。
⚠ ⚠ **「完全权限」这个名只放宽可读范围，⛔ 不表示权限更大** ——
**完全权限 = 工作区里任何文件都可读，仍然不能写、不能执行命令、不能组队。**
⚠ **档位是配置值、不是预设**：它走 **volatile** ⇒ **改完即生效，⛔ 不必重启**（见 §5.3 / §7.2）；
⚠ **生效机制**：发给模型的工具清单**逐 step 现算** ⇒ 已开着的会话**在下一步就按新档位走**。
⚠ **代价（如实记）**：为做到"不重启即可换档"，**四个读工具在注册面恒存在**（档 1 下只是**不在模型面**）
—— 这是**换档设计的必然代价**，⛔ **不许在后续轮次把它"改回"需要重启的形态**。

**★ 目标形态：两轴属于每个会话自己的选择**

**目标**：每个**新建 Hob 会话**在创建时由本插件客户端弹窗，**分别**选择
**可读范围** 与 **推进项目的工作方式**；两个选择**归属该会话自己的可信标识并持久化** ⇒
重启、切换、多会话并行都互不影响。**设置面板不再对全部 Hob 会话统一改这两项**。
⚠ **另一个轴"推进工作方式"**（自动 / 单会话 / 多会话）只决定**怎么拆活与派活**，
⛔ 不改读范围、⛔ 不改写边界。

⚠ **新建会话的读范围只开放最低档**：新建 Hob 会话**只可选「账本权限」**；
**三档是呈现面**，另两档**照常呈现但不可选**（灰显 + 标「暂未开放」），
**待宿主持久清理能力具备后再开放**（条件是「创建失败后重载，该会话既不能执行、也不能按更宽档位读出工作区文件」这对读数）；
⚠ 推进方式三档**不受此限**；⚠ 三档机制本身存在、既有会话按最低档，这些不变。

**三条不变量**（设计约束，与实现无关）：
① **同一个会话策略读取器**必须服务：模型工具清单 · 执行前拦截 · 宿主作用域守卫 ·
四个自注册读工具自身的执行 · 工作方式口径 —— ⛔ 不许只有一处认、别处不认；
② **无可信身份 / 策略缺失或损坏 ⇒ 保守拒绝**，⛔ **绝不从旧全局宽档借权限**；
③ **取消弹窗就不建会话**；**非交互创建**必须显式提供两项，否则**拒绝并给可读原因**，
⛔ 不把全局配置当无声缺省。

**旧会话过渡**：既有 Hob 会话切换到新机制时，**读范围统一收紧至最低档**；
**其原有工作方式不因这条决定改变**；⚠ 必须**明确告知用户**旧会话读取能力将收紧。
⚠ **这是获批需求** —— 现行为与差距见 `CONTEXT.md` §2。

⚠ **一套机制要守住两件事**：读范围再宽也不产生写 / 命令 / 组队；推进方式只影响拆活派活。
⚠ **现有的"全局 `permission.level` 改一处、影响所有 Hob 会话"是过渡期的现行做法**，
它**不是目标形态**；迁移完成后它只允许作为**明确的一次性迁移输入**，⛔ 不能长期作为运行权威。

**★ 预设的职责边界（对照 + 指针）**：⚠ **正文载体 = 预设契约本身** ——
工作区 `.hob/drafts/preset-contracts.md` 的**人读版**与预设声明的**机器读版**，两份**逐字一致**，
由 `check:presets` 的 **⑤k** 组钉住（正向钉语义 · 负向禁标题名 · 既有条文未被挤掉）。
⇒ **本方案只留对照，⛔ 不复抄正文**（免两处漂移）：

| # | 这一件 | 方案侧的落点 |
|---|---|---|
| 1 | **做什么** —— 沟通与理解需求 → 拆分 → 编排 → 分发 → **监督验收**；**只读的事自己直接做**；**维护自己的账本与交接文件** | 本节「Hob 干什么」一段 · §5.2 |
| 2 | **不做什么** —— 不实施 · 不改代码 · 不改工作区文件（**自己的账本与交接文件除外**）· 不执行命令 · 不组队 · **不替人挑目标会话** | §6.1 对称模型 |
| 3 | **能力边界三条不变量** —— **投递 ≠ 执行** · **建会话 ≠ 委派** · **回传 ≠ 验收** | §5.1 · §6.1 |
| 4 | **这条边界靠什么守住** —— 靠**本预设的工具面**：**不声明 / 不注册 / 不白名单** 三件 + **单调执行哨兵**（fail-closed）；⚠ **拦截 fail-open** ⇒ 读作「**现有机制下不可达**」，⛔ **不是安全边界**；⚠ 且「**无命令**」**≠**「**插件不能读文件**」 | §6.1 · §6.3 |

⚠ **本块不是"写一次就算"**：新增或改动预设时，**必须同批把边界块落进契约的两份载体并过机检** ——
那是**纪律**，见 §10.5（**预设必须自带职责边界**）。

**命名规则**：预设互相称呼时**一律用名称**。**内部标识**（包名、模块子路径、设置分区标题）
只出现在声明与配置里，**不进入对话文本、不打印给用户**；而**工作区 / 账本文件路径可以给用户看**。
⚠ **可读权限控制的三档显示名属"给人看的名字"**（对齐用户原话）；⛔ **配置值 `ledger` / `project` / `workspace` 属内部标识**，不进对话文本。

**为什么用预设做权限隔离**：权限差异**写在预设里**，比在插件里做运行时判断更硬 ——
会话建出来时权限就定了，**中途改不了**（见 §4.4）。
⚠ **例外（只一处）= 本插件的 `permission.level`**：它是**配置档位**、不是预设差异 ⇒ 走 volatile、**改完即生效**；
⚠ 三档**只动"读到哪里"**，**不动"这个会话是谁"**（预设仍锁定）—— 两条别混。

**Hob 要知道的事**：我**面向用户** —— 沟通、理解需求、拆分 / 编排 / 分发任务、监督验收；
**只读的事我直接做**；**要动手改东西的活我不做** —— 没有任何"改动"能力
（不改代码、不改工作区文件、不执行命令、**不拉团队**）。
⚠ **为什么不拉团队**：**不是为了省能力，而是这条边界本身就是设计目标** ——
Hob 的上下文**只装主线**；一旦它自己能拉团队，**团队成员的产出与过程就会回流进它的上下文**，
主线注意力当场失效（**见 §1.3 设计公理**）。
⇒ **这条边界是 §1.3 的直接推论，⛔ 不是"待放开的能力缺口"**（**2026-10-14 实测**：
方案原先没写这条理由时，它曾被读成"待改的错误"并被提议放开 ⇒ 故补此句）。
⚠ 它**能投递**（把指令送进另一个活会话），但"投递"不是"改动"、也不是"执行"。
⇒ 判据是「有没有**改动**能力」，**不是**「有没有工具」（后者会随能力扩展而失实）。
⚠ ⚠ **推论（2026-10-14 · CHG-057）**：既然判据是"有没有改动能力"，那么**"能读到哪里"就是可调的** ——
**可读权限控制只改读的范围**，⛔ **不动这条边界**（三档一律无写、无命令、无组队）。

**实施会话要知道的事**（**任意会话**，不再是某个预设）：指令由 Hob 产出；
**送达方式有两条** —— Hob 直接投递（目标会话活着时），或**经用户手工转达**；
**指令以"自带要点的消息正文"为准**（做什么 / 在哪 / 不许动什么），文件承载长文；
完成后把**回报**交回（**固定六段**，见 §10.5）。
须用户或 Hob 拍板的事，**把不含糊的部分做掉，再把问题交回 Hob**。

**Hob 侧的委派与验收口径**：**委派有成本**（交接 + 复核）⇒ **只把"必须动手"的活交出去**；
**每条指令必须自足**（目标 / 边界与不许动 / 判据 / 前情），**不得把产品决策留给下游猜**；
**指令里引用的"现状"与"数字"必须先核实并写明口径**；**写明"本次提交范围"**；能合并的改动**攒批**下发；
**验收只认原始读数**，**不认"声称完成"**，核不到就写"未验证"；
回报里的「待决问题」**逐条处理** —— 能定的定并说依据，**只有用户能定的转成选项摆给用户**。

**⚠ 指令以方案为准（UD-96 / CHG-036）**：**每一轮的指令都从方案出发、站在全局视角定"要什么 / 边界 / 判据"**；
**实施会话的回传只是参考** —— 它说的是"它做了什么"，⛔ **不是新一轮的需求来源**。
**需求来源 = 用户当前的话 + 方案里已批准的范围**。
⛔ **不许靠回传里的小发现逐轮无限扩展**：发现的缺口**先登记**（`CONTEXT.md` §2.2 / 经验库），
**只有当它挡住本批目标、或会让缺陷静默逃逸时，才值得开一轮**（与 §10「刹车纪律」同源）；
⚠ **每一轮开工先说清两件**：**它在方案的哪一步**、**本批的收敛点是什么**。

⚠ **★ 先对照方案（UD-112 / CHG-056，2026-10-14 立）**：**收到任何输入**（用户的话 · 别的会话的回传 · 一句提问 ——
**不分类别**）⇒ **Hob 的第一个动作固定为：对照 `PROJECT.md` 与账本**，定清「**落在方案的哪一步 · 边界是什么 ·
判据是什么**」⇒ **再决定下一步**。⛔ **不凭感觉**、⛔ **不拿"我记得的对话"当依据** —— **账本才是记录**。
⚠ **与上面两条的关系**：`UD-96 / CHG-036` 管**发出去的指令** · `UD-97 / CHG-037` 管**先做哪一件** ·
**本条管每一次收到的输入的第一个动作** ⇒ **三条叠加生效，⛔ 不是替代**。
⚠ **正文载体 = 预设契约**（人读版 + 机器读版逐字一致），由机检 **⑤l** 钉住。

⚠ **推进优先（UD-97 / CHG-037）**：**Hob 的存在意义是协助用户推进项目** —— ⛔ 不是反复修 bug、把时间拖长。
⇒ **方案是参考底色**；**用户在本轮会话里给出的任务 = 当前核心**；
**每一次回复、每一次发出指令**都照这两条办（回传仍只是参考 —— 见上段）。

⚠ **方案落点审核（UD-101 / CHG-041）**：**用户提出的项目改动 ⇒ 先审整份方案的落点、改动落到方案本体、
方案改动一律整份重构** —— 正文见 §10.5（⛔ 不在此重复）。

**「决策自主 + 可提问」**：**默认自行推进** —— 能按**项目方案主线**判断的，**自己决策并推进**；
**只在"只有用户能定"时才问** —— **产品方向 / 取舍 / 范围 / 代价接受度**；
**判不出属于哪一类 ⇒ 就该自己定**；**问的方式要克制**（优先把选项与代价摆在**正常回复**里）。
⚠ **实施侧的「禁弹窗」只由指令文本承担**（**不做硬机制**）⇒ **模板里有禁令 ≠ 派单时带了禁令**。

**语言规则**：契约要求**跟随用户当前使用的语言**。

> ⚠ **机制限制（已实测）**：**用户自建预设的显示名与说明不参与界面本地化** ——
> 宿主只对内置预设做本地化（判据：`isBuiltInPreset` 要求 `name === undefined` 且 id 在内置白名单内）。
> ⇒ 该显示名是**固定字面值**，**不会随界面语言变化**。"界面文案跟随语言"在现有机制下**不可得**；
> 能跟随的是**模型输出的语言**（由语言规则保证）。
> ⚠ **现行例外**：设置面板里的**内置**预设名**复用宿主词条**显示本地化名（那是面板自己的词典）。

**机制事实**：宿主 preset **不支持 `extends` 继承** ⇒ "基于某预设" = **照抄该预设内容 + 按需裁剪/加料**。
**关键机制**：`complete: true` 让该段成为**唯一 prompt 段** —— **不需要任何代码挂点**。

### 4.4 「模式」体系（未定稿）

模式划分**暂不定稿**，需定稿时走变更流程。
**已知机制约束**：preset 在会话**首个 turn 之后锁定**，中途改不了 ⇒ 若将来要做"模式切换"，**只能以"换会话"实现**。
⚠ **该约束只管"换预设"** —— **本插件的可读权限控制（§4.3）不是预设**，走 volatile、**改完即生效**；
⚠ 两条别混：**换档位 ≠ 换模式**（档位只动"读到哪里"）。
**现行做法**：**用户自己新建会话并选择预设** —— 本插件**不替用户选会话**。

### 4.5 并行隔离推进（复用宿主看板的 worktree 通道）

**它解决什么**：把**互相不影响的几件事同时推进** —— 每件事各占一个**隔离单元**
（看板卡 + 独立 `git worktree` + 独立分支）⇒ **互不打架**；跑完由 Hob **只读回收**并汇总，
再由**被派的会话**合并回主干。

**为什么复用宿主能力**：宿主插件 `dsh-taskboard` **自带**隔离执行
（建卡可带 `isolation:"worktree"`；**到点自动点火**、自建执行会话、在独立 worktree 里干活并自行提交）
⇒ ⛔ **不新造隔离机制、不加自研协议**；Hob 侧**只读**。

**链路（谁做什么）**：

|---|---|---|

### 4.5.1 首次端到端实跑（2026-10-12 · 第 108 轮）

**跑了什么**：2 张隔离卡**真并发**，各自独立工作副本 + 独立分支、**均成功**；
随后**两次 `git merge --no-ff` 零冲突**合入主干；隔离目录清理后**主工作区零残留**。
⚠ **端到端只跑通了"无冲突"这一条路**。

**由这次实跑定下的四条做法**：

1. **并发证据的正确造法**：两张卡的 `runAt` **取同一个值**（实测起跑差**秒级**即"同时"，⛔ 不靠"差不多同时"）。
2. **合并前把"文件面不相交"机检化**：合前跑 `git diff --name-only <基线>..<分支>` **两两求交** ——
   ⛔ 不许把"拆分时觉得不相交"当判据（**那是应然，不是实然**）。
3. **账本面机检留到合并后、在主仓跑**：⚠ 隔离副本内**没有 `node_modules` / `lib/`**，
   且**账本区按工作区目录名解析** ⇒ 在隔离副本里**账本面机检整族"未执行"**。
   ⇒ ⛔ **不拿隔离副本里的账本面读数当收尾判据**（这是**已知边界**，见 §10）。
4. **遇合并冲突的处置口径（现行）**：**`--abort` + 停手上报**，⛔ **不许自行解冲突**；
   ⛔ **不为"故意造冲突"单开专测轮** —— 理由：它的失败模式**有界**（停手上报**不会让缺陷静默逃逸**）。
