# UD-115 · 会增长的表与文档：**设计之初就要写明"到顶怎么办"**

**用户原话**（2026-10-15 · 分两段，同批记）：

> 这类像日志的表，不该每一次改动都往里加一行；应该像日志一样，每次改动留一个小的日志小文件，每次留下的就是一个文件，而不是反复往同一张表里追加。

> 注意：这些改动不只是针对当前项目。这个项目本身是用来管理其他项目的——所以当它被安装到其他实例、供其他用户在其他环境中使用时，能不能同样具备这些契约、这些约束、这些提示，能不能达到同样的使用效果，而不是只对当前项目有效。

> 你管理的账本、每一张表格、每一份文档，在设计之初就要考虑清楚——尤其是那些会一直增长的表：从最开始就设计好它在达到上限之后该怎么办，或者如何避免达到上限，而不是等到了上限之后再去解决。

**决定（三条，第一条是本条的核心）**：

1. **设计期要求**：**凡会一直增长的表 / 文档，在它被建立的那一刻就要写明「到顶怎么办」**（另起册 · 分区 · 派生 · 滚动窗口 … 取一），⛔ **不许"先长着，到顶再说"**。
2. **可增长载体的默认形态**：**一轮 / 一条一个文件**（写一次固定），⛔ **不往同一张表里逐行追加**。
3. **可搬运性（本条的适用范围）**：⚠ **以上两条不属于本项目专属** —— 它们是**骨架（可复用层）的规矩** ⇒ ⚠ **必须随骨架走**：装到别的实例、别的用户、别的环境，**新开的工作区拿到的是同一套约束与提示**，⛔ **不许只对本项目有效**。

**依据（据实说明，非用户原话）**：
- **同一缺陷已出三次**（第 182 / 204 / 207 轮：从轮次表滚出的行**无槽位**）—— ⚠ **前三次修法均为"补回去 + 写成规矩"，三次都复发**；
- ⚠ **根因** = **那张表只进不出，却住在一份每轮被整份重写、且必须一次读完（上限 64KB）的文件里** ⇒ **增长必然撞上限** ⇒ **"裁掉几行"成为随时可用的动作，而没有任何东西在那一刻拦得住**；
- ⚠ **骨架里已有同族的先例**（`.hob/INIT.md` §3.2.1「编年体陷阱」）—— ⚠ 但它**只覆盖 `CONTEXT.md` 一种**，⛔ **未覆盖"每轮 / 每立一条纪律 / 每次归档各加一行"那类表**。

**关联**：**UD-103 / CHG-047**（改动须连账本与可复用层一并照顾 —— 判据 = "这套骨架换个工作区开箱，得到的是新规矩还是旧规矩？"）· **UD-114**（轮次登记改一轮一文件）· **UD-83 / UD-95 / UD-99**（账本形态）。
