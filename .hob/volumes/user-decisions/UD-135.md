### UD-135 · 2026-10-18 · 「简要说明」要写成不懂代码的人能懂的：⛔ 不许堆技术细节

- **决策内容**：**每轮回复里给用户看的那一段（`简要说明`）必须用常人的语言写** ——
  用户对象是**不懂代码的产品决策者**，读那一段是为了**对项目有把控**，不是来读日志的。
  ⛔ **不许**把路径 / 行号 / 提交号 / 字节数 / 命令名 / 检查名 / 退出码 / 模块编号 / 英文标识符堆进去；
  ✅ **要说清三件**：**这轮做了什么** · **项目现在什么状态**（好还是坏）· **要不要你决定什么**（附代价）。
  细节**不丢**，留在账本与报告件里；用户问就展开，不问不铺。
- **用户原话（逐字）**：
  > 「我说的是你前面回复的图片红框内的，这些信息，这里是给用户看的当前会话轮次指令的简要说明,这个项目明确说了用户对象是不懂代码的用户，你要用常人可以明白的语言去描述本次本轮给实施会话的指令的说明，让用户对项目有一定的把控，这个太复杂了，需要对当前项目的HOB预算的轮次回复信息格式做一定的调整」
- **为什么（用户给的理由）**：「这个太复杂了」—— 那一段**本该是给人看的**，却写成了给人核对的。
  ⚠ **这是本项目第一次被明确指认「格式反了对象」**：`实施指令` 给会话看、技术点加密没问题；`简要说明` 给用户看，技术点堆上去就**等于没有说明**。
- **不做（边界）**：⛔ 不改 `实施指令` 段的技术密度（它本来就是给实施会话读的）· ⛔ 不改**回报六段**（实施侧格式）·
  ⛔ **不因为要"简单"而省掉"未验证 / 风险"那一块**（那是把控的实质）。
- **落点**：**CHG-061**（回复格式 v8：`简要说明` 的写法与判据 + 预设契约两份载体同批）。
- **状态**：active
- **关联**：CHG-061 · CHG-060 / UD-134（两板块定名与精简）· UD-58 / CHG-008（格式沿革）
