# UD-126 · 派活口径修正：**指令只保主线，细节开放**（⚠ 取代 `UD-122` 第一条的"五要素逐项写死"）

**用户原话**（2026-10-16 · 逐字）：

> 你派的指令错的这样导致实施会话报错然后返回这种，应该想法办法避免至少要减少这种问题出现，我是这样想的就是有可能指令错误是你给的指令太复杂太僵硬了，你是根据方案给落实指令的，你给的指令主要是为了方案落实，应该给怎么落实还有怎么验收验收标准就可以了，哪些不影响方案落实不会造成方案偏差的可以开放性让实施会话自己做就是你需要做的是根据方案以及用户指令保证主线落实就可以了，不需要管太多太细致的，不然你肯定会出错或者说你没办法把握住太细的动力，你只需要保证方案的主线就可以了，你来想想应该怎么做调整，还有整个项目内各种的提示詞类的信息不能太复杂各种逻辑交叉这样不利于理解容易出错，所有提示詞类的信息应该简单明确

**决定（⚠ 四条，Hob 据此改派活方式）**：

| # | 内容 |
|---|---|
| **1** | ⚠ ⚠ **作业书只写三件**：**① 要落实什么（对应方案哪一步）· ② 怎么验收（验收标准 / 判据）· ③ 不许碰什么（硬边界）** —— ⚠ ⛔ **不再逐条写做法、步骤、手法、清单** |
| **2** | ⚠ ⚠ **凡不影响方案落实、不会造成方案偏差的细节 ⇒ 开放给实施会话自己做**（⚠ 手法、顺序、临时件放哪、怎么取证 —— ⚠ 只要它写在报告里、可复核） |
| **3** | ⚠ ⚠ **Hob 的职责收窄为"保证主线落实"** —— ⚠ ⛔ **不追求把细节都摁住**（⚠ 理由：**摁不住，且必出错** —— ⚠ 本轮实证：一处指令写法把分界线画错、硬造出一个"做不到"） |
| **4** | ⚠ ⚠ **全部提示词类信息（作业书 / 报告模板 / 纪律条文）须**简单明确**** —— ⛔ **不许逻辑交叉、⛔ 不许一条里塞多档多例外**（⚠ 判据：**读一遍就能照着做**） |

⚠ ⚠ **与 `UD-122` 的关系（⚠ 不冲突，⚠ 收窄其第一条）**：
⚠ `UD-122` 第一条规定"指令要说清 做什么 / 用什么技术方案 / 怎么做 / 最终效果 / 怎么验收" ——
⚠ ⚠ **本裁定把后两项保留为**必写**（怎么验收 = 判据），⚠ 而**"用什么技术方案 / 怎么做"降为**按需****：
⚠ ⚠ **只有当"选错做法就会造成方案偏差"时才写**；⚠ **其余交实施会话自定**。
⚠ ⚠ **`UD-122` 第二 / 三条（发现不符即停手汇报 · Hob 回方案核、⛔ 不打补丁）⛔ 不变，仍然生效。**

⚠ ⚠ **配套（Hob 立的可执行化）**：
- ⚠ ⚠ **停手门槛随之抬高**：⚠ **只有"方案的落点做不到 / 会偏离方案"才停手**；⚠
  ⚠ **做法自由、取证自由、顺序自由** ⇒ ⚠ ⛔ **不许把"我的指令写得不细"当成停手理由**；
- ⚠ ⚠ **Hob 复核时改口**：⚠ **以前是"核指令里的做法对不对"，现在是"核主线有没有偏"**。
