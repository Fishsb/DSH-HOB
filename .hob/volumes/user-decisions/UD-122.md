# UD-122 · 派活口径：指令要说清"怎么做"，实施方**发现与指令不符 ⇒ 立即停手汇报**（⛔ 不许自己找方法）

**用户原话**（2026-10-16 · **逐字照录**；⚠ 原话里的"实施绘画"按上下文即"**实施会话**"，⚠ 本件不改原字）：

> 有一个问题就是实施绘画：你给的指令一定要明确。你就想象一下，这就是一个公司，你是总负责，你派活的时候，你派给实施绘画的，你肯定要说清楚要怎么干：这个是什么技术、什么方案、要怎么干，要达到的最终效果是什么，用什么技术、用什么技术方案、用什么方式。
>
> 还有实现逻辑是什么，你肯定要编排清楚。然后还要给他说清楚：如果跟你说的这个东西有不一样的地方，他应该立即停止，并且把问题汇报给你，而不是他自己去想办法。因为他自己是落实的，你是负责根据方案来派活的，你有一个全局的视野，实施绘画是没有的；他自己去找方法解决问题，可能会最终导致整个方案有一定偏差偏离。虽然这个可能对整体没有大的影响，但是你知道，整个你这个编排任务、整个项目落地的过程中有多少个环节，每一个环节都偏离一点，每一个环节偏一点，它最终都会在最后爆发出来，变成总体的一个偏差，最终要花费更大的精力才能去给他揪过来。而且很多还会有噪音偏差，就是应该你说什么，他就怎么干。
>
> 跟跟你说的东西一旦有不一样的地方，他应该立即停止，然后跟你再沟通，让你想办法，让你去告诉他下一步应该怎么办。你呢，这个时候应该怎么办？一旦对方报的有任何跟你派出去指令——就是你本来的、你给的、根据方案来的指令——你把根据方案来的指令交给实施绘画去干，实施汇报如果发现有问题，他反馈给你，那说明你给人的指令就有问题。当你给的指令有问题的时候，这时候不应该是让他接着干，而是你来返回来，再根据方案以及实施绘画返回的问题，你要思考一下：这个问题是不是方案有问题？是方案有问题，还是说你给的指令有问题？要去找是哪一块出了问题。
>
> 如果这个方案本身的落实方案、这个方案本身这个技术，或者是逻辑哪一块有问题，你应该做的是把方案重新审核，然后去修改方案，然后给实施会话指令，让他进行下一步。如果是你给的指令（有问题），那就要修改。我的意思就是说，如果实施会话根据方案给的指令做不下去，那说明你给的指令、说明方案就有问题，你应该回来找方案的问题，而不是应该硬着头皮去找什么绕圈子去找、打补丁去解决问题。

**决定（⚠ 三条，Hob 逐条落）**：

| # | 内容 |
|---|---|
| **1** | ⚠ ⚠ **派活指令必须"完整可执行"**：⚠ **做什么 · 用什么技术/方案 · 怎么做 · 最终效果是什么 · 用什么方式** —— ⛔ **不许只给目标、让实施方自己补做法** |
| **2** | ⚠ ⚠ **实施方发现"与指令说的不一样" ⇒ **立即停止** + 汇报**（⚠ ⛔ **不许自己想办法、不许绕路、不许换做法**）—— ⚠ **理由（用户给）**：⚠ **落实方没有全局视野**；⚠ ⚠ **每个环节偏一点，会在最后合成总偏差**（⚠ 即"**噪音偏差**"） |
| **3** | ⚠ ⚠ **Hob 收到汇报后 ⇒ **回方案核**：⚠ 是**方案**的问题还是**我把方案翻成指令时翻错了****？⇒ ⚠ **方案有问题就改方案**（⚠ **只有用户能批准方案变更，Hob 只提议**）· ⚠ **指令有问题就改指令** ⇒ ⚠ ⛔ **⛔ 不许"硬着头皮绕圈子、打补丁"** |

⚠ ⚠ **两档分界（Hob 判 · 属本裁定的可执行化，⚠ 不是削弱）**：
⚠ **(甲) 做法 / 可行性不符**（⚠ 指令说的做法做不到 · 报错 · 实现逻辑走不通 · 盘上实情要求换做法）⇒ ⚠ ⚠ **停手汇报**；
⚠ **(乙) 纯事实读数过期**（⚠ 只是某个数 / 某份文件与记法不符，⚠ **而"怎么做"完全不变**）⇒ ⚠ **按实测办 + 登记**（⛔ 不停手）。
⚠ ⚠ **判据**：⚠ **甲档 = "要不要换一个做法"**；⚠ ⚠ **判不出 ⇒ 按甲档办（停手）**。
