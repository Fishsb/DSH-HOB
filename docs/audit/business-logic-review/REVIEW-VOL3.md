## §6 高影响待验证项（**不进缺陷总表主排序**）

> 这一节存在的理由：本次审计有两条发现**静态不可证**。把它们写成「已确认」是不诚实的；把它们删掉是不负责的。
> 处理方式：**单列、标明缺什么证据、给出获取证据的具体做法**。它们**不计入 §1.2 的 100 条**。

### 6.1 C-01（原 blocker，**已降级为观察项**）· primitives 是否在宿主模块表 seed 里

- **原判**：t5 标 blocker —— 若成立则设置分区、阶段面板、门禁横幅、创建弹窗**全部消失**，且失败点在 factory materialize 阶段，界面上没有任何提示。
- **主控复核后的判定（§10.3）**：**证据不足，降级**。
- **降级理由（逐条）**：

| 证据 | 实际能证明什么 |
|---|---|
| `atoms.tsx:5-8` 注释「真机实测：宿主浏览器模块表没有这个包」 | **只是一句注释**，无探针脚本、无输出 |
| `tsdown.config.ts:13-17` 注释「实测 seed 含它」 | **同样是注释**，且**与上一条矛盾** |
| `lib/client.js:28` 确实有 `require("@deepseek-ai/dsh-client-ui-primitives")` | **只证明产物里有 require**，不证明该 require 会失败 |

- **三条证据里能作为事实的只有第三条**，而它恰恰是两条注释都认可的共同前提（不论 external 与否，产物里都会出现这个 require）。
- **真正的未知**：「宿主模块表有没有这个 seed」，而**仓内没有任何机检覆盖它**（t5 已 `grep` 确认 `check-client-deps.mjs` 零命中）。
- **为什么不能算 blocker**（主控的三条理由，本文档采信）：
  1. 若它成立，`lib/client.js:28` 的 require 会抛，**所有用户都会立刻遇到**，属「必然暴露」而非「静默失败」；
  2. 与本次审计主题（业务逻辑审查）关联度低，属构建/宿主集成问题；
  3. 仓内两条注释互相矛盾这件事本身**值得记录**，但那是「注释不可信」问题，不是「客户端不激活」问题。
- **怎么定论（一条探针即可）**：`scripts/host-probe.mjs` 已有骨架；实读 `__DSH_BOOT__` / `__dshSidebarModuleSystem__.seed` 的键集合，把「primitives 在不在 seed 里」变成可复现读数。
- **顺带记录**：`check-client-deps.mjs` 应新增一条「产物里的每个 `require` 必须在宿主 seed 白名单里或显式标注为 external」——**这是把「注释互相矛盾」变成「机检会红」的唯一办法**。

### 6.2 t4 P-06（**未验证**）· `PERMISSION_SERVICE` 缺席即 throw 导致工具面全不注册

- **原判**：t4 标 medium。
- **为什么静态不可证**：该条涉及宿主进程内服务缓存形态。静态读码只能确认「`PERMISSION_SERVICE` 的取值无人读」这一半；「旧版 `config.ts` 缓存 ⇒ `apply` 抛错 ⇒ 工具面全不注册」属**运行时时序**。
- **能确认的部分**：`src/preset/tools.ts:361-371` 确实 `throw`；而该服务的**取值**无人读（`config.ts:598-606` 自承「唯一消费者是 `serviceNameOf('PERMISSION_SERVICE')`，取到的档位值从不参与判定」）。
- **为什么值得记录**：一旦成立，整个预设 `apply` 抛错 ⇒ 工具面**全部不注册**；而它「保护」的东西根本不从它取值 ⇒ **这次停摆换不到任何安全收益**。
- **怎么定论**：需要真机 apply 期读数——在宿主进程里注入一个旧版 `config.ts` 缓存，观察 `apply` 是否抛错。**本文档不把它写成已确认。**
- **若成立的修复**：把 `throw` 降级为 `degrade(...)`（与 `WORK_MODE_SERVICE` 同档），或直接删掉该依赖；若机检 G-11 钉着「缺席 ⇒ throw」，需同批改判据并写明理由。

### 7.1 D-1 · 用户批准是否允许由 Hob 转录（**本次最重要的一条**）

**问题**：`decided_by = "user"` 由 `hob_pipeline_approve` 自己写死（`tools.ts:2081`），唯一校验是对自填 `source` 做正则（`:2051-2058`）。Hob 只需拼一句「确认需求 R-01 第 1 版」即可通过。而「用户回执」在工具契约里被定义为**一段字符串**，不是**一次用户操作**——当前架构里根本不存在「用户直接触发工具」的通路。

| 选项 | 内容 | 效果 | 代价 |
|---|---|---|---|
| **A** | 在 `hob-write.ts` 白名单层把 `unit-pipeline-approval.toml` 设为**仅该工具可写**（该路径从 `LEDGER_PATH_RE` 排除，改由专用函数写） | 批准只有**一条写入路径** | 那条路径本身仍由 Hob 调用、`decided_by` 仍是硬编码常量 |
| **B** | 保持现状，改为在**门禁侧**核 `source` 必须匹配 `approvalReceiptPattern` | 把校验下沉到所有写入路径 | 只是把同一个判据抄第二份（`R-15` 同类病），且被校验方仍是写入方 |
| **C** | **引入用户本人触发的通路**：批准由用户在 UI 点击产生，或 decision 单元必须携带**宿主可验证的消息 id / 用户输入摘要** | 判据的输入来自**被校验方之外** | 需要 UI 与宿主事件流配合，改动面最大 |

**推荐：C。**
**理由**：**A 优于 B，但 A 不足以解决根本问题**——A 只是让批准只有一条写入路径，而那条路径本身仍由 Hob 调用、`decided_by` 仍是硬编码常量（`tools.ts:2081`）。
**⇒ 仅 C 能实质修复 I-4；A/B 都只是把可绕过点收窄，不改变「被校验方即写入方」的自证结构。**

**与 t2 D-1 的关系**：t2 提议 A 或 B、推荐 A；t4 D-1 推荐 B（「改为用户本人操作」）。**主控与本文档采信 t4 的方向（C），并把 t2 的 A 作为过渡步骤。**
**建议落地顺序**：先做 A（低成本、立即收窄攻击面）→ 再做 C（实质修复）→ B 可并入 C 的校验下沉，不必单独做。

**怎么证明修好了**：
- A：`write_hob('ledger/units/unit-pipeline-approval.toml', …)` ⇒ 必须被拒。**负向对拍**：放开该路径 ⇒ 断言红。
- C：decision 单元必须携带 `decided_by_message_id`，该 id 能在**宿主会话事件流**里查到、且内容匹配回执模式；伪造一个不存在的 message id ⇒ 必须被拒。**这是唯一能证明 I-4 成立的断言。**
