## §102 A 方案 **第 13 轮** · `stageFmt` 升级为**多占位符**

### 102.1 升级了什么

**改前**（单占位符）：

```js
function stageFmt(key, name, value) {
  const tpl = stageText(key)
  const token = '{' + name + '}'
  if (!tpl.includes(token)) return tpl
  return tpl.split(token).join(String(value))
}
```

**改后**（任意个占位符）：

```js
function stageFmt(key, vars: Record<string, unknown>) {
  let out = stageText(key)
  for (const name of Object.keys(vars)) {
    const token = '{' + name + '}'
    if (out.includes(token)) out = out.split(token).join(String(vars[name]))
  }
  return out
}
```

⚠ **为什么改签名而不是加一个 `stageFmt2`**：
  两个函数做同一件事、只是参数形态不同 —— 那正是本仓反复记的「两个语义源」。
  ⇒ 一个函数、接受对象，**调用点也统一了**（`{ n: v }` 而不是 `'n', v`）。

⚠ 顺带把已有的 **7 处单占位符调用**一起改成对象形态 ——
  否则同一个函数会有两种调用风格，下一个人不知道该学哪个。

## §114 修一个**偶发失败**（flaky）：WPR-4 在 `check:all` 里偶尔红

### 114.1 现象与定位

| 跑法 | 结果 |
|---|---|
| 单独跑 | EXIT=0（43/43） |
| **连跑 8 次** | **0/8 失败** |
| **在 `check:all` 里** | ✗ WPR-4 失败（实测 1 次） |

**根因**：`advanceWorkPlans` 是 **fire-and-forget**（`orchestrator.ts:4685` 用 `void`），
它内部有**盘 I/O**；而 `waitFor` 只用 `setImmediate` 推进 ——
**只推进事件循环，⛔ 不保证 I/O 完成**。

⇒ 单跑时 400 轮够；`check:all` 里 47 族串行、磁盘繁忙时**偶尔等不到**。

### 114.2 修法：轮数 400 → 2000

```js
const waitFor = async (fn, rounds = 2000) => {   // ← 原 400
  for (let i = 0; i < rounds; i++) {
    if (fn()) return true
    await new Promise((r) => setImmediate(r))
  }
  return fn()
}
```

⚠⚠ **这是「加重等待」，⛔ 不是「放宽判据」**：
  判据本身（**B 轨道必须被派出**）**一个字没动**。
  改的只是「愿意等多久」—— 而等待的对象仍是**可观测结果**（`h.delivered` 里有 B）。

⚠ 仍**不用 sleep 猜时长**：每轮都是 `setImmediate`，I/O 一完成立刻返回。

### 114.3 验证：**在磁盘负载下**压测

单跑通过不能证明修好了（改前单跑也 8/8）。所以本轮**人为制造负载**：

```bash
for i in 1 2 3; do dd if=/dev/zero of=/tmp/stress$i bs=1M count=200 & done
# 同时连跑 10 次 check:work-plan-runtime
```

**结果**：`负载下失败: 0 / 10` ✅

⚠ 这一步是关键：**只在「原来失败的那个条件下」验证，才算验证。**
  改前的 400 轮在负载下会偶发失败；现在 2000 轮 10/10 通过。

### 114.4 ⚠ 与「假绿」的区别

本会话抓到过 **6 次「判据空转」**（判据说绿但其实没检查），那类修法是**加强判据**。
这次相反：**判据是对的，只是等得不够久**。
两种问题的修法完全不同：

| 类型 | 症状 | 修法 |
|---|---|---|
| 判据空转 | 改坏实现也绿 | 加强判据 + 负向对拍 |
| **偶发失败** | 单跑绿、负载下偶红 | **加重等待**（⛔ 不动判据） |

⇒ 必须分清这两类，否则会把「等得不够」当成「判据有问题」去削弱它。
