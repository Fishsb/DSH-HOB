### 168.3 ⛔ R-12：**根因一字未改**

`pipeline.ts:617`：

```ts
if (decisions.length > 0 && revision <= maxApprovedRevision) {
  out.push({ rule: 'C-23', unit: id,
    why: `内容已变但 revision 未递增（已有决定最高第 ${maxApprovedRevision} 版，当前第 ${revision} 版）` })

```

⚠ **`decisions.length > 0` 这个短路条件就是缺陷本身** ——
   它让「首次批准前」整段免检。

REVIEW 原文（含主控裁定）：

```

  ⇒ 首次批准前的每一次内容改写都不需要递增 revision，digest 随之漂移，

主控裁定（§4）：应**升级为 high** —— 它让「批准绑定具体修订与摘要」
在**首次批准这一最关键节点**上失去可验证性。
```

### 168.4 ⚠ 为什么 R-12 我不改

```
去掉 decisions.length > 0 后：任何新建需求只要改过内容就报 C-23。
而**新建需求在首次批准前本来就会反复改写**（那是起草期）。
⇒ 需要先定义「起草期」与「待批准期」的边界，
  否则会把正常起草行为全部判成违规。
⛔ 那不是修 bug，是改语义 —— 需产品决策。
```

⚠ 可能的正确方向（⛔ 未实施，仅记录）：
```
① 引入 draft 状态：status === 'draft' 时免检，进入 proposed 后开始强制
② 或要求首次批准时**记录当时的 digest**，后续变更与之比对
    （这与 R-12 的建议「批准绑定具体修订与摘要」一致）
```
