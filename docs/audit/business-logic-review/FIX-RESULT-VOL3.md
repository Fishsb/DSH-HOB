## §50 本轮复核 O-11：**REVIEW 的判断与既有设计冲突，已驳回**

### 50.1 REVIEW 说

> 首波部分失败即把整份计划置 `failed`，与「仍有 running 轨」并存
> ⇒ 修法：首波部分失败不直接置 `failed`，仍按 `trackStates` 派生
> ⇒ 机检：**3 轨 1 失败 2 在跑 ⇒ 计划 `state` 不得为 `failed`**

### 50.2 我按它改了，然后断言**当场抓到我改错了**

```
✗ WPR-39 · 1 轨失败 + 2 轨在跑 ⇒ 计划却显示 failed（O-11 复发）：running=2
```

⚠ 我已把首波那处改成 `workPlanProgress(...).nextState`，**但计划仍然 `failed`**。
查下来：`workPlanProgress` 自己的派生规则是

```ts
const failed = plan.tracks.some((track) => stateOf(track) === 'failed')
const nextState = failed ? 'failed' : terminal ? 'joining' : 'running'
```

⇒ **只要有一条轨失败，`nextState` 就是 `failed`** —— 与首波那处**同一个语义**。

### 50.3 这个语义是**有意的**，不是缺陷

`work-plan.ts:963` 的注释写明：

> - 依赖轨只在全部前置 `returned` 后进入 ready；
> - **前置失败/取消 ⇒ 该轨取消，计划失败**；
> - 只有全部轨道进入终态后才允许 `joining`，不能因为首波已派出就提前汇合。

⚠ 理由（读代码得出）：**多轨计划的轨道之间有依赖链**。
一条轨失败 ⇒ 依赖它的轨**永远不会 ready** ⇒ 整份计划**不可能成功**。
此时把计划标成 `running` 是**谎报**：它看起来还会推进，实际已经死了一半。

⇒ **`failed` 是对的**：它说的是「这份计划**不会成功了**」，而不是「所有轨都停了」。
「仍有 running 轨」与「计划已失败」**可以并存且应当并存** ——
那几条正在跑的轨回传时，由 `closePlanProblems` 拦（「有 N 条轨道失败 ⇒ 失败计划不能收成 completed」）。

### 50.4 结论：**驳回 O-11**，不改代码

| 项 | 结论 |
|---|---|
| REVIEW 的判断 | ❌ **不成立** —— 它把「计划状态」当成「轨道状态的聚合」，而实际语义是「这份计划还会不会成功」 |
| REVIEW 的机检要求 | ❌ **与既有设计冲突**，若采纳会让「计划已死一半」被显示成 `running` |
| 代码改动 | **已全部撤销**（`orchestrator.ts` 恢复 `plan.state = failed > 0 ? 'failed' : 'running'`） |
| 断言 | **已删除**（它与既有设计冲突，留着会挡住正确行为） |

⚠⚠ **这是本轮最重要的产出**：我按 REVIEW 改了一处**本来正确**的代码，
是**自己写的断言**把它抓回来的。

⇒ 教训：**REVIEW 的「怎么证明修好了」不是圣旨** —— 它也是审计时的推断。
  动手前先问：**现有实现是不是有理由的？** 有理由就记下来，⛔ 不要为了「符合 REVIEW」而改。

⚠ 这与 §34 的教训互补：那次是「文档说未修、实际已修」；
  这次是「文档说该改、实际不该改」。**两次都是文档落后于代码。**

## §52 本轮修 O-25 · 门禁不再用 `alert()`

### 52.1 缺陷本体

```ts
onClick: () => {
  if (!canOpen || sessionId === undefined) {
    try { globalThis.alert?.(`${gateText(selected)}\n${gateButtonUnavailableText()}：${t('gate.alert.unavailable')}`) }
    catch { /* 无 alert 环境 ⇒ 静默 */ }
    return
  }
}
```

⚠⚠ **为什么该删**（三条，都不涉及「样式偏好」）：

| # | 理由 |
|---|---|
| ① | **它不是无障碍通道** —— 屏幕阅读器对 `alert()` 的朗读依宿主而定，而 `aria-label` / `title` 是标准属性，一定被读 |
| ② | **它阻塞** —— 一个「说明为什么不能开」的提示不该抢走焦点 |
| ③ | **它可能不存在** —— `globalThis.alert` 在 jsdom / 部分宿主里是 `undefined`，改前的 `try/catch` 就是兜这个。**一个要兜底才能用的通道，不是好通道** |

### 52.2 ⚠ 但**不能**简单删掉 —— 代码注释已经写明为什么不用 `disabled`

```
// ⚠ 不能开时**不用 disabled**：disabled 的按钮在部分宿主主题下读不出来，
//   且用户不知道"为什么点不动"。改成可点 + 可读说明（见 onClick）。
```

⇒ **删掉 alert 而不管「为什么点不动」，就是把那条注释的意图一起删了。**

### 52.3 修法：说明**不减**，副作用**消失**

```ts
title: canOpen ? gateText(selected) : `${gateText(selected)}\n${buttonText}：${t('gate.alert.unavailable')}`,
'aria-label': buttonText,   // ⚠ 保持按钮语义
```

| 项 | 改前 | 改后 |
|---|---|---|
| `title` | 恒为横幅文案 | **随能否打开而变**（不可用时带完整说明） |
| `aria-label` | `buttonText` | `buttonText`（不变） |
| 不可用时点击 | 弹 `alert` | **无操作**（说明已在 `title`/`aria-label`） |
| 可读性 | 依赖 `alert` 是否存在 | **标准属性，一定可读** |

⛔ **没有改回 `disabled`** —— 注释已写明部分宿主主题读不出来。
⛔ **没有「什么都不说」** —— 那是把「用户不知道为什么点不动」这条病重新引入。

### 52.4 ⚠ 断言编号又撞车（第 4 次）

先取 `G-28`（已占用）→ 实测该族编号空间已到 **G-313** → 改 `G-314`。

⚠ 这是第 4 次（§33 `CU-41/42`、§39 `S-33i/j`、§40 `WPR-27/28/38`、本轮）。
⇒ **纪律（已第 4 次写，必须真的执行）**：
  取号前**必跑** `grep -oE 'X-[0-9]+' <该族脚本> | sort -u -V | tail -3`。

## §63 本轮修 O-10 · 推进器重入不再静默丢弃

### 63.1 缺陷本体（已实测）

```ts
const advancingWorkPlans = new Set<string>()
...
if (advancingWorkPlans.has(key)) continue     // ← 静默丢弃
advancingWorkPlans.add(key)
try { ... } finally { advancingWorkPlans.delete(key) }   // ← 只删，不补跑
```

⚠ 推进有**四条路**会撞上（派单后 / 回传结算后 / 就绪扫描 / 状态读取）⇒
推进进行中来的那一次**被直接丢掉**，而调用方以为已经推过了。

⚠ 后果：**盘上计划停在旧状态**，要等下一次触发才补上 —— 而「下一次」可能很久。
这与「漏派」不同：**计划面看起来推过了**。

### 63.2 修法：`Set` → `Map<key,{dirty}>`

| 时机 | 动作 |
|---|---|
| 命中（已在跑） | **置 `dirty = true`** 然后 `continue`（⛔ 不是裸 continue） |
| `finally` | 若 `slot.dirty` ⇒ **再跑一遍** |

⚠ **只补一次**：补跑期间再来的请求会让 `dirty` 再次为 true，
但那一次由**下一轮外部触发**处理 —— 否则这里是**活锁**。

### 63.3 ⚠ 负向对拍的两种写法（第一种「崩了」）

| 尝试 | 做法 | 结果 |
|---|---|---|
| 1 | 把 `Map` 改回 `Set` | **脚本崩溃**（`Set` 上没有 `get`）⇒ 输出为空 |
| 2 | 保留 `Map`，去掉 `dirty` 置位与补跑 | ✅ **2 条红**，且点名缺什么 |

⚠ **第 1 种不是「负向对拍成立」，是「脚本崩了」** —— 两者在输出上都是「没有 ✓」，
  但前者说明断言有牙，后者说明**整族没跑**。
⇒ **纪律：负向对拍输出为空时，先看脚本是不是崩了**（`tail` 完整输出 + 检查退出码）。

⚠ 这是第 3 次同类（§31 脚本崩溃 / §41 替换没生效 / 本轮 Set 崩溃）。
