## §136 ⚠⚠ **自我纠正**：上一轮说的「改签名就能去掉 `as any`」低估了范围

### 136.1 上一轮我写了什么

```
§135.4 可⾏解：把 isPipelineV3 的参数类型从 Record<string, unknown> 改成 object
       ⇒ 对外 25 个调用点全部可以去掉 as any（其中 11 处现在带 as any）
```

⚠ 那句话**技术上成立**，但**范围判断错了**。

### 136.2 本轮实测：范围远大于「一个签名」

```
带 as any 的 5 个文件（同源问题）：
  src/shared/stage-controls.ts      23
  src/shared/pipeline-view.ts       17
  src/shared/stages-index.ts        10
  src/modules/tools.ts               2
  src/shared/requirement-chain.ts    2
  ──────────────────────────────────
  合计                              54

而 Record<string, unknown> 在 src/ 里有：
  69 处 · 横跨 25 个文件
  其中 pipeline.ts 独占 25 处
```

⇒ **这不是「改一个签名」，而是要重新设计一整层的类型契约。**

### 136.3 ⚠ 而且那个设计**是有意的**，不是疏忽

```
账本单元是动态 TOML（字段随 kind 变化：req / change / task / verif / acc …）
⇒ 用 Record<string, unknown> 表达「未知形状的键值表」是**正确的建模**；
   ⛔ 不能为了消掉 as any 就把它强成具体 interface。
```

⚠ 真正的问题不是 `Record<string, unknown>`，而是：

```
具名类型 StageControlUnit（interface，无 index signature）
   ⇄ Record<string, unknown>
两者之间没有**显式的**转换通道 ⇒ 只能靠 as any 硬跨
```

⇒ 正确解法有两类，**都不是一行签名的事**：

| 方案 | 做法 | 代价 |
|---|---|---|
| A | 给 `StageControlUnit` 加 `[k: string]: unknown` index signature | ⚠ 会**削弱**该类型的所有字段检查（`u.anyTypo` 不再报错） |
| B | 抽一个 `asRecord(u)` 显式转换函数，替代所有 `u as any` | ✅ 保留两端类型强度；⚠ 要改 54 处调用点 |

⚠ **方案 B 是正解**，但它是**一次独立的重构**，⛔ 不是本轮顺手能做的。

### 136.4 结论

```
· §135 的「根因定位」是对的（interface 缺 index signature ⇒ TS2345）
· §135 的「可行解」方向对，但**低估了范围**（以为改 1 个签名，实际是 25 个函数的类型契约）
· 本轮**不改代码**，改为把范围与两个方案写清
· 下一步若要做，必须单独一轮 + 全程用 check:hob-gate(59) / check:stages-dom(148) 兜底
```

### 136.5 ⚠ 教训：说「可行」之前先量范围

```
我上一轮的推理链：
  发现 TS2345 → 试出 object 能过 → 就说「25 个调用点都能去掉 as any」

缺的一步：
  ⛔ 没数「有多少个函数用了 Record<string, unknown>」
     （数了就会发现是 69 处 / 25 文件，而不是 1 个函数）
```

⚠ **「能编译通过」≠「改动范围可控」**。
   这是本轮最值得记的一条：可行性验证只证明**第一步**走得通，
   ⛔ 不证明**整条路**的代价可接受。

## §138 ⚠⚠ **重大发现：commit 不是「保存工作」，而是叠在一条未 push 的功能分支上**

### 138.1 我之前**从未查过**的事实

```bash
git rev-parse --abbrev-ref HEAD   → codex/item-presentation
git rev-list --count master..HEAD → 10
git rev-list --left-right --count HEAD...@{u} → 无上游
```

⇒ 当前状态：

```
* codex/item-presentation   5ee0797  ← 我们在这里，领先 master 10 个提交
  codex/progress-panel-ia   80cae75
  master                    80cae75
  ⇒ **没有上游**（从未 push）
```

⚠⚠ **这意味着三件事**：

| # | 含义 |
|---|---|
| ① | 151 个未提交变更会**再叠 10 个提交**到一条功能分支上 |
| ② | 这条分支**从未 push**，所以 master 上看不到那 10 个提交 |
| ③ | 如果直接 commit，结果是一条 **10+N 个提交、无上游、未合并** 的分支 |

### 138.2 ⚠ 为什么这条重要

我前面 40+ 轮一直在说「等你拍板 commit」，但**从没说清 commit 到哪**。
如果用户以为「commit = 存到 master」，而实际是「存到一条未 push 的功能分支」，
那是**预期与结果不符** —— 即使我照做了也是错的。

```
我之前的问法：「要 commit 吗？」
           ⇒ 信息不足，用户无法判断

应该的问法：「当前在 codex/item-presentation（领先 master 10 个提交、无上游）；
              151 个变更要提交到这条分支，还是新建分支，还是先看 diff？」
```

⚠ **这就是「问对问题」和「问了问题」的区别**。

### 138.3 ✅ 三条可选路径（都已验证可行）

| 路径 | 操作 | 后果 |
|---|---|---|
| A | 四批 commit 到 `codex/item-presentation` | 该分支变 10+N 提交；仍未 push |
| B | 从当前 HEAD 建新分支再提交 | `codex/item-presentation` 保持原样；新分支承载全部变更 |
| C | 不提交，保持工作区 | 151 个变更仍有丢失风险（无 commit 即无保护） |

⚠ **C 是当前状态，也是风险最高的状态** —— 任何误操作都可能丢掉 151 个文件的改动。

### 138.4 ⚠ 与 §89（`.gitignore` 吞掉 152 个文件）的联系

那次事故的症状是「`git status` 突然归零」。
如果当时有 commit 保护，损失会小得多。
⇒ **未提交的工作量本身就是一种风险**，不只是「还没做完」。

### 138.5 本轮没有执行任何 git 写操作

```
git commit / git branch / git push  —— 一个都没跑
只跑了只读命令：rev-parse / rev-list / branch -v / log -1
```
