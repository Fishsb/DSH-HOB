② **目录形态的引用也核其内文件**（⚠ 第 106 轮实证：断言 D 只 `existsSync(目录)` ⇒

**(b) 盘上派生**（`archive/` 下**每一个子目录** —— ⛔ **不按 `README.md` / `sources/` 过滤**）。
⚠ 判定行**分别报两个来源的贡献**（⛔ 不报一个合计数 —— 合计数会把"覆盖面降了"藏起来）。
⚠ **为什么(b)不收窄**：**任何"收录判据"都自带一个被排除面** —— 第 121 轮曾按"有 README 或含 sources/"收，

### 负向对拍：**通过判据不只是退出码**

> **负向对拍的通过判据 = 退出码非零（`exit ≠ 0`）** **且** **输出里有可读的断言行**。

⚠ **只判退出码不够** —— 实测踩过（`EXPERIENCE.md` **E-112**）：被检查对象的形状被改坏时，
**检查脚本自己先崩**（如对 `undefined` 裸访问 `.length`），同样 `exit 1`，
但输出里**一条可读的 ✗ 行都没有**（只剩一段堆栈）⇒
**分不清"抓到了违规"与"检查器崩了"**，看日志的人还得反推"它本来想查什么"。
⇒ 判据必须**两条都看**：先看**有没有失败**（退出码），再看**失败长什么样**（有没有指名的断言行）；
新增/修改断言后，除了正向跑，**还要拿"被检查对象的坏形状"喂一次**（否则那条路径永远跑不到）。

### 样本登记：**新增"引用类"断言必须自带"不该被咬"的样本**

> **新增 / 修改"引用类"断言时，必须同步给它加至少一个"不该被咬"的样本**（进**断言 E** 的样本数组）。

⚠ **为什么**：断言**只会验证它枚举到的形状** —— **枚举漏了，它就是静默失效**
（⚠ 与 **E-70 / E-73** 的"清单少列一项就静默出错"同形：**清单漏一项，机检不会报**）。
⚠ 出处（`EXPERIENCE.md` **E-114**）：D / D′ 上线一轮后，正本新增了
**描述它们边界的文本**（`archive/DATE-NAME/` 这类举例、`TASK-Rnn.md` 这类反例示意名），
宽口径正则把这些**当成引用** ⇒ **断言被描述自己的文本打挂**。
⇒ **纪律**：改 D / D′ 的判据时，**同步看断言 E 的样本够不够**；
新增任何"扫原文里的引用"的断言，**先给它配"不该被咬"的样本**再上线。

⚠ **本条对"渲染标记"类断言的落地（2026-10-11 第 49 轮实测补）**：
**围栏豁免 ≈ 那条"不该被咬"的样本** —— 断言 I 扫正本找未渲染标记，
而"讲这个标记怎么写"的正文**必然**要写出标记 ⚠ **所以渲染器与断言必须共用同一份
"跳过围栏"的实现**（`hob-render.ts` 的 `scanMarkers`），否则会出现
"文档里按 A 口径能安全写、机检按 B 口径报残留"的自相矛盾。
⚠ **实测边界（第 50 轮已修正）**：豁免覆盖**两种"形状可排除"的形态** ——
① **围栏代码块内**（块级）；② **行内代码段（code span）内**（行内，反引号串**长度须匹配**）。
⚠ **裸写的标记照旧被咬**（那是**真残留**）——豁免**不覆盖**它。
⚠ **第 49→50 轮的教训**：豁免最初**只有围栏**，于是"行内引用"照旧被咬，
**文档在正文里复述这个形态就被自己打挂**（**E-125** 实测：Hob 的 `CONTEXT.md` 那句）

### 跑检查的**标准姿势**：先建输出目录，再取退出码

> ⚠ **跑收尾命令前先 `mkdir -p` 输出目录**；**取完退出码确认日志已落盘**（如 `ls | wc -l` 等于命令条数）。

理由（`EXPERIENCE.md` **E-115**）：`npm run X > 某不存在的目录/x.log` ⇒ **重定向失败**，
shell 把**整条命令**报成失败 ⇒ `EXIT=1` 会被误当成**命令报错**（**假报障**）——
⚠ **被测命令其实一次都没跑**。
⇒ **报 FAIL 前先复核那条命令的原样输出**（失败时输出**往往是空的或只有 shell 报错**，
与"断言 FAIL"的 `✗` 行形态完全不同）；
**先问一句"这条命令真的跑起来了吗"**，再判它对不对。

### 清理类改动的验收**必须包含 `build`**：扫描器 PASS ≠ 文件能编译

> ⚠ **清理类改动（尤其动不可见字符 / 删字符）的验收必须包含 `build`**。

理由（`EXPERIENCE.md` **E-121**）：**删掉的字符可能是"承重"的** ——
实测：清掉 `src/modules/orchestrator.ts` 注释里的一个 U+200B 后，
`build` 与 `typecheck` **双双 EXIT=2**（`tsc` 上百条语法错误）。
根因：那个字符**恰好夹在 `*` 与 `/` 之间**，使得注释结束符**从未真正出现**；
删掉它 ⇒ 结束符成立 ⇒ **块注释提前闭合**，其后整段代码成了裸文本。
⇒ **"零宽字符扫描器报 0 处"只说明"没有不可见字符了"，证不了"文件还编译得过"** ——
**两条判据各自必要、都不可省**：**清理后必须重跑 `build`**（本轮即靠它当场把哑弹引爆、未让坏产物进入提交）。

### 读数可信：**读数必须能指认到"哪条命令的哪一行输出"**

> ⚠ **凡在提交信息 / 文档 / 回报里出现的读数，必须能指认到「哪一条命令的哪一行输出」**；
> **指认不出就写"未取"**。

理由（**第 42 轮实证**）：曾有一处**提交信息**写了**没测过**的 `BUILD-STAMP` 读数
（写 `dirty=false` + 一个 `built_at`，**实际是 `dirty=true`、且无该行**）——
⚠ **形态不是"过期"，是"根本没有"**；与 **`EXPERIENCE.md` E-117**（写死预期值）同族，**但更重**：
过期的值至少**曾经为真**，补出来的值**从头到尾没有对应的事实**。
⚠ **更值得记的一层**：**提交信息不是被检查的对象**（机检只扫正本与骨架，**不扫 git 提交信息**）
⇒ 它天然是**无人核对的区域** ⇒ **最不该出错的地方反而没有防线**。
⇒ **提交信息里的读数与正文读数同标准**（⛔ 别因为"它不会被机检"而放松）；
**写前先看一眼日志**（成本一条 `tail`，远低于事后认账）。
