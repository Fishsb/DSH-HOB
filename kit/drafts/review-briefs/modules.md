# 审查简报 · 编排模块（`src/modules/`）

> 按 [`_TEMPLATE.md`](./_TEMPLATE.md) 的四节写。⚠ 只写四节，**不加节**。

## 一、失败长什么样

这个目录是**协调层**：投递、唤醒、路由、工具入口。它碰的是**时序**，
所以失败形态是「动作发生了，但没人知道发生了」。六种（都实测过）：

1. **重入丢请求**：用 `Set` 记在跑的推进 ⇒ 第二次请求被静默丢弃 ⇒ 盘上计划停在旧状态。
   现在是 `src/modules/orchestrator.ts:4346` 的 `Map<…,{dirty}>` + `finally` 里补跑（O-10）。
2. **首次派发跳过门禁**：多轨门禁从盘上找计划，首次派发时找不到 ⇒ 落到「只报健康」⇒ 一路放行。
   判据是 `check:work-plan-runtime` 的 `WPR-40`（⚙ 给了「没有批准 ⇒ 拒派 + 零投递」的夹具）。
3. **打错门吞成业务失败**：路由 404/405 若被当「账本坏了」⇒ 人按看到的去修**错的东西**。
   客户端侧的出口是 `StaleRouteError`；工作计划侧是 `reason: 'route-error'`。
4. **写业务判决的动作不过闸门**：`src/modules/orchestrator.ts:10807` 的 `LEDGER_WRITING_ACTIONS`
   （verify / accept / send-back / close-delivery）—— 少了这一层，被隔离的会话**仍能写判决**（O-35）。
5. **不校验「那个会话真的存在」**：多轨的 `sessionId` 只判非空 ⇒ 拒绝原因分不清
   「没派」与「派了没人跑」（`src/modules/orchestrator.ts:4805` 的 `session-not-found`，O-39）。
6. **同一段逻辑被多个实例同时跑**：门禁轮询若三个槽各跑一遍，实际频率是注释的 2–3 倍（O-19）。

## 二、该跳过的路径

| 路径 | 为什么跳过 |
|---|---|
| `*-route.ts` 里的 HTTP 包装（header / 序列化） | 只是传输层；要审的是「它把失败映射成什么 `reason`」 |
| 工具 `description` 的文案细节 | 文案漂移由预设侧与判据侧各管一半，⛔ 不在这里逐字抠 |
| 一次性迁移分支 | 由 `check:ledger` 覆盖；审它要连带审「迁移后谁重核」 |

## 三、建议上限

**小问题 ≤ 3 条**；「某一**类**动作都没过闸门」**合并成一条**并列出动作名。

⚠ 本目录的问题一旦成立，往往是**一类**而不是一个（四个动作、三个实例、两条路由）。
逐个报会让人以为改一处就完事。

## 四、证据要求

- 协调层的问题必须给**时序**：先 A 后 B 会发生什么。只说「没有校验」不算证据。
- 说「静默」时给出**观察点**，并说明为什么那个观察点读不到。
- 涉及「多个实例」的，给**实例数量**与**实测频率**（⛔ 不给「可能有几个」）。
