# 质量门禁（Gates）—— 阶段与门禁的判据

> **性质**：**骨架 · 进 git**（可复用、可分发、零外部依赖）。
> **来源**：改编自 [dsh-expert-mode](https://github.com/Asher-2000/dsh-expert-mode)（**MIT 许可**）
> 的 `.expert-mode/methods/quality-gates.md`（**逐字采用其规则表**；⚠ 该文件的**行数不引用** —— 行数会随它自身改动漂移）。
> **配套**：角色见 `.hob/templates/ROLES.md`；指令与回报见 `TASK.md` / `REPORT.md`。
>
> ⚠ **本文件不是"再写一套流程"** —— 它是把 SDLC 的各个阶段**变成可判定的门禁**，
> 且**每条判据都能落到读数**（命令退出码 / 文件字节 / 审计态）。

---

## 0. 一句话

**说不清完成标准就不开工；实现者自己说"没问题"不算数。**

---

## 1. 触发条件（满足任一即启用门禁）

1. 任务类型属于**高风险**：架构选型 / 合同审查 / 金融分析 / 安全加固 / **生产代码**
2. 任务复杂度 **≥ 3 个步骤**（需跨角色协作）
3. 用户明确要求"**多角度验证 / 把关 / 审核**"
4. 协调方判断输出将**影响决策或生产环境**

> **简单任务**（单文件、问答、聊天）走 **Fast Track 直通**，不启用门禁。

---

## 2. Pipeline v3 正式六阶段与 G6 交付门

```
需求规格 → 实现方案 → 任务图 → 任务执行 → 技术验证 → 产品验收
                                                        ↓
                                  G6 交付收口（skipped / standard / strict，按风险启用）
```

### 阶段 1：需求规格（G1）

**做什么**：把模糊需求变成**可验收的规格**。

- 用户确认目标、边界、关键例子、可接受代价和当前修订
- Hob 复述目标、扫描歧义、登记问题与假设、写出可观察验收条件
- 产出：需求单元 + 用户确认记录（`decision_kind=stage-approval`）
- 🔒 **铁律：内容齐全不等于用户批准；`agreed` 与「继续」都不算批准**

**判据**：无阻塞问题；假设不是 `pending`；关键例子有预期结果；验收条件可观察；
用户明确确认需求 ID 与当前修订。

### 阶段 2：实现方案（G2）

**做什么**：把已批准需求变成可执行、可验证的方案基线。

- 至少一个合理路径；`medium` 及以上比较至少两个可行路径，或说明唯一可行原因
- 写出路径取舍、推荐理由、需求映射、测试 / 回归策略和交付范围
- 完成固有风险评定：硬触发六段式事实、十维事实、规则版本和输入摘要
- `high` 风险要有独立设计评审；`critical` 还要双评审证据或用户明确授权
- 产出：方案单元 + 用户确认记录（绑定当前修订、路径和内容摘要）
- 🔒 **铁律：方案内容变化必须递增修订；旧批准和旧风险评定同时失效**

**判据**：用户批准当前修订并选中合法路径；方案内容、验证策略和风险评定均绑定同一修订；
任何硬触发都不能被总分平均降级。

### 阶段 3：任务图（G3）

**做什么**：把已批准方案拆成可独立执行、可独立复核的任务 DAG。

- 每个任务有自包含任务书、反例、停手条件、回流目标、预算、证据计划
- 每个任务声明 `task_risk`、风险原因、触及面和不可逆动作
- 高风险任务必须隔离、独立复核、串行并给出回滚证据
- 两个任务写同一或嵌套路径时，必须显式串行或拆清写范围
- 产出：无环、无悬空依赖、覆盖全部验收条件的任务图

**判据**：任务图 Ready；所有验收条件都有任务覆盖；任务风险声明完整；
写范围冲突已串行化或被拒绝；任务不超出父方案授权范围。

### 阶段 4：任务执行（G4 前置）

**做什么**：由开发会话执行已派发的任务，Hob 跟踪并收集证据。

- 执行单元绑定当前任务修订和真实任务号
- 每个任务回传小步验证读数；命令类证据必须有可复跑命令和整数退出码
- 产出：执行记录、证据、回传件和未做到事项
- 🔒 **铁律：派发不等于执行，执行回传也不等于技术验证通过**

**判据**：每个任务都有当前修订的独立运行记录；执行回传有真实读数；
运行记录不能顶替另一个任务的验证或验收。

### 阶段 5：技术验证（G5 前置）

**做什么**：独立验证者逐条核对已批准需求、技术证据和风险控制。

- 验证单元绑定当前任务修订；验证者和独立会话都不得是实现者
- 每条验收条件有对应证据；证据必须是当前修订可复核的原始读数
- 高风险方案按硬触发逐项给出风险控制证据 `risk_review_refs`
- 新发现且方案未声明的风险不能 PASS，必须回 G2 重评
- 产出：当前任务自己的技术验证结论、非符合项和残余风险输入
- 🔒 **铁律：最新结论优先；旧修订 PASS 不能掩盖新修订退回；测试通过不自动等于产品接受**

**判据**：每个任务都有自己的当前 PASS；非符合项已关闭或明确退回；
证据、验收条件、控制措施和任务修订都可追溯。

### 阶段 6：产品验收（G5）

**做什么**：用户判断已验证结果是否满足原始目标、可接受取舍和残余风险。

- 独立验收会话不等于实现者；产品确认、用户例子逐条结果和技术证据齐全
- `high` / `critical` 残余风险须有接受人、影响范围、触发条件、监控 / 回退方式和接受条件
- 有条件接受必须逐条登记 `liens`：负责人 | 期限 | 影响 | 关闭证据
- 退回必须写清 `back-to-requirement` / `back-to-plan` / `back-to-task`
- 产出：产品接受、有条件接受、退回、延期或拒绝的用户决定
- 🔒 **铁律：技术验证通过不等于产品接受；产品接受也不等于交付已放行**

**判据**：产品决定明确且绑定当前结果；用户例子逐条可核；
残余风险已由用户或授权人接受；有条件接受有可追踪整改项。

### G6：交付收口（产品验收之后，按风险启用）

**做什么**：在产品验收之后决定是否发布、部署、交付或归档。

- `skipped`：必须有 `skip_reason` 和决定者，风险要求 strict 时不得跳过
- `standard`：构建、冒烟、回滚路径和发布后检查证据齐全
- `strict`：额外要求独立发布审批、回滚 / 恢复演练、发布后监控、残余风险接受
- G6 必须绑定 `chain_acceptance_ref`、`risk_assessment_ref`、`residual_risk_decision_ref`
- 仍有未关闭整改项、`open` 风险或不可接受的 `handling` 风险时不得收口
- 产出：已收口、按风险跳过或受阻的交付记录

**判据**：`chainCompleted` 与 `deliveryClosed` 分开；
产品已接受但交付未放行时显示 G6，而不是伪造产品验收失败。

### 集成与收尾

- 汇总角色产出、技术验证与产品验收决定；有分歧时由裁判处理，仍不决上报用户
- 交付时附：哪些经过门禁、哪些按风险跳过及原因

### 风险如何决定门禁深度

风险从方案事实推导，不由模型自评降档。硬触发优先；十维中任一维达到最高值、
多个高风险维度叠加，或高风险叠加难恢复条件，都不能被平均掉。每条硬触发写清
`trigger | fact | affected | evidence | mitigation | residual`；任务执行风险另记
`task_risk`，决定拆小、隔离、独立复核、串行与回滚证据。完整矩阵见本项目的
风险策略规格与共享规则模块。

## 3. 门禁规则速查（**逐字采用上游**）

| 规则 | 内容 |
|---|---|
| **最多重试** | 验证/审查失败**最多回炉 2 轮**，仍不过则**上报用户决策** |
| **评审独立性** | **审查专家 ≠ 实现专家**（跨领域评审） |
| **记录留存** | 所有阶段在任务板**留历史，可回溯** |
| **跳过门禁** | 用户明确要求 / 低风险任务，但**需告知用户"本次跳过了门禁"** |

## 4. 与任务板的配合（推荐工作流）

```bash
# 1. 创建主任务 + 子任务（依赖关系）
taskboard create "设计用户系统" --owner architect --desc "完成标准: ER图+API+安全方案"
taskboard create "实现用户系统" --owner backend-dev --dep task-001
taskboard create "验证用户系统" --owner qa-engineer --dep task-002
taskboard create "独立审查" --owner security --dep task-002 --desc "安全评审，独立于实现"

# 2. 查看看板
taskboard status

# 3. 认领执行（角色完成后 done）
taskboard claim task-001 architect
taskboard done task-001 "ER图+API设计完成"

# 4. 依赖完成后自动转 ready，继续下一环
taskboard list --status ready

# 5. 失败重试 / 冷启动恢复
taskboard fail task-002 "接口超时"
taskboard retry task-002
taskboard recover   # 崩溃后恢复 stale running
```

> ⚠ **本项目有两种任务板，按可用性择一**（见 §5 降级）：
> · **Agent Teams**（`team_task_create` / `team_task_*`，**DSH 原生**，一定在）
> · 上游的 `taskboard.py`（**Python 脚本**，需自行落地，落盘可审计）
> 上表用 `taskboard` 泛指；**实际用哪个由项目决定**。

## 5. 降级路径（**可移植性硬要求**）

⚠ 依据**可移植性口径**（⚠ **出处见本项目账本，骨架不点名具体编号**）：**外部插件换环境即无** ⇒ 每个环节必须有降级方案。

| 缺什么 | 降级做法 |
|---|---|
| 缺 **Agent Teams** | 串行执行 + 人工在 `.hob/` 账本记录进度 |
| 缺 **圆桌（roundtable）** | 用 `spawn_teammate` 招独立成员做评审 |
| 缺 **看板（taskboard）** | 用 `archive/<日期>-<slug>/` 目录 + `TASK.md` 当任务板（⚠ 归档目录在**账本区**，不在工作区） |
| 缺 **搜索类工具** | 用原生 `web_fetch` 直接取 URL |
| **完全没有子代理能力** | ⚠ **仍可执行**：角色化为"**同一会话内分阶段扮演**"，门禁不改——**只有"独立性"降级为"分轮次"**，须在交付时**如实说明** |

> 🔒 **底线**：**门禁规则本身不因降级而消失**；降级只影响**由谁执行**，
> 不影响**判据**。交付时须写明实际用了哪一档。
