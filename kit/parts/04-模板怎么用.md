## 4. 模板怎么用

`templates/` 下是**空骨架**，只含格式，不含任何本项目内容（**份数以 `ls kit/templates/` 实测为准**）：

1. **新建账本**：以模板为蓝本创建运行数据文件，替换 `[日期]` / `[谁]` 等占位。
2. **格式参照**：需要确认「某类条目该有哪些列」时，以模板为准。

**改账本结构时，必须同步改模板**（否则漂移）。

### 4.1 需求卷与索引**怎么写**（技术操作说明 —— **⛔ 不进 `REQUIREMENTS.md` 根**）

> ⚠ **为什么单列在这里**（2026-10-22）：需求根只记"用户要什么"。而**文件名怎么起、编号列写什么、
> 索引怎么加一行、哪条机检在盯着** —— 这些是**维护这本账的方法**，属**骨架使用说明**。
> ⚠ 把它们写在需求根里，会让读需求的人**第一条读到的是操作步骤**而不是功能目标；
> ⚠ 也会让"需求是否纯净"这件事**无法机器判断**（判据边界见 §4.1.4）。

#### 4.1.1 一个条目 = 一个文件

- 文件名 = `REQ-<两位编号>.md`（如 `REQ-01.md`），放在 `volumes/requirements/`。
- **正文写进卷文件**，⛔ **不写 `REQUIREMENTS.md` 根**（根只是地图）。

#### 4.1.2 每个条目四块

**用户要实现的功能** · **可观察的完成条件** · **旧会话/迁移语义**（若适用）· **来源**（指向用户原话出处）。

- ⚠ **来源只写出处指针**，⛔ 不复述用户原话全文 —— 原话在 `archive/` 的归档件里，
  两处各存一份必然各自漂。

#### 4.1.3 索引与根要**两处同批**

新增一条需求时，三件事必须**同批**做：

1. 新建 `volumes/requirements/REQ-<编号>.md`；
2. 在 `volumes/requirements/INDEX.md` 的表格加一行（编号 / 目标 / 条目）；
3. ⚠ 同时在 `REQUIREMENTS.md` 根的「当前功能需求」表加一行 —— **两处同批**，否则两向完整性会红。

⚠ **编号列写文件名主干**（`REQ-01`，⛔ **不是裸 `01`**）——
机检 **L 组**按「编号列 ↔ 文件名主干」逐行核。

#### 4.1.4 哪条机检在盯这本账（**判据边界，照实读**）

| 机检 | 管什么 | ⚠ 不管什么 |
|---|---|---|
| **L 组**（`check:gitignore`） | 索引两向完整 · 编号列 ↔ 文件名主干 | ⛔ 不管内容语义 |
| **A 组**（`check:gitignore`） | `REQUIREMENTS.md` 与模板的**节名一致** | ⛔ 不管正文像不像需求 |
| **U 组**（`check:gitignore`） | 需求面**不许出现**日期 / 工具名 / 拒绝 reason / 变更编号 / 机检名 / 过程词；**并且不许出现独立的技术维护附录**（标题含「怎么写 / 如何写 / 维护 / 操作步骤 / 机检口径」等，或正文出现「写进…」「加一行…」「两处同批…」这类**操作指令**） | ⛔ **不做语义判别** —— 只咬**结构性技术附录**与**词形**，见下方边界声明 |
| **T 组**（`check:gitignore`） | 写入工具的**可写面**（新根可写 / 旧根拒写 / 旧根仍可读） | ⛔ 不管文档内容 |

⚠ ⚠ **U 组的边界必须照实说**（**不许把「词形全绿」叫「语义全净」**）：
它证明的是「**没有**那几类可枚举的技术痕迹（含结构性附录）」，
⛔ **不证明**「剩下的每一句都是用户功能需求」—— 后者**只能人工读**。
⚠ 判据的**设计目标**是「**结构性违规可机检 · 语义纯度靠人**」，⛔ 不是「用正则冒充语义理解」。
